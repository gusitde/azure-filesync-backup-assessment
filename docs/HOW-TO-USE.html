Azure File Sync and Azure Backup - assess an estate, build one, connect your own servers, and take it all apart again. This is the long-form guide; every screen, every decision, and the reasons behind the ones that cannot be undone.

Start here

One command opens everything. Nothing changes without showing you first and asking.

cd <the kit folder>
.\start.ps1

The shape of the thing

The kit answers two different questions, and it is worth knowing which one you are asking before you start.

Assess

An estate already exists. Export it read-only, and get findings against roughly eighty rules. Needs nothing but Reader.

Build

Nothing exists, or the customer will not share what does. Build the target design from four inputs, then connect real servers to it.

Both converge on codex/ - the blueprints that describe the target state, the playbooks that build it, and the runbooks for when it breaks.

Deployment settings

Four inputs decide everything. The rest is derived, and every derived value is yours to override.

The four things only you can answer

InputWhy it is asked
Entra global adminUsed once, by phase 1, to create the deployment identity and grant it a role. Never used again.
Subscription and name prefixWhere it is built, and the one naming decision you make.
AD admin accountCreates the storage account's object in your directory. Needs the right to create an object in one OU - not Domain Admin.
AD basicsDomain, NetBIOS name, the OU, and whether the object is a computer or a service logon account.

Derived, not fixed

A prefix of contoso in eastus produces:

rg-contoso-filesync        the resource group
stcontosofs01              the storage account
sss-contoso-filesync       the Storage Sync Service
rsv-contoso-eastus         the Recovery Services vault
vnet-contoso-filesync      the virtual network
dnspr-contoso-eastus       the DNS Private Resolver

Change the prefix and all six move together. Set one explicitly and it stops following - the settings screen marks which is which with (derived). Clearing a value hands it back.

Why this mattersConsistent names are not cosmetics. When someone finds rsv-contoso-eastus in six months, the prefix tells them which estate it belongs to and the suffix tells them the region. A hand-picked name tells them nothing.

Remembering your own machines

The onPremises section holds the file server, the folder for each share, and your DNS servers. Fill it in and the wizard offers those values instead of asking cold - and, just as usefully, it shows the shape of the answer it expects.

"onPremises": {
  "fileServer": "fs01.corp.contoso.com",
  "serverPaths": {
    "dept-shares": "D:\\Shares\\dept-shares"
  },
  "dnsServers": "dc01.corp.contoso.com, dc02.corp.contoso.com"
}

You do not have to edit the file. Answer the questions once and the wizard writes them back for next time.

A gap worth knowingSettings are read when phase 1 writes the deployment context. Build re-runs phase 1 and picks up your edits. Resume deliberately does not - it exists to continue a deployment already under way. The settings screen warns you when the two have drifted apart.

Build

Two phases. The first needs a person; the second needs nobody.

What phase 2 does, in order

  1. Preflight. CLI version, sign-in, subscription access, the dns-resolver extension, and the five resource providers the build needs - registering any that are not. A subscription that has never used a service has its provider switched off, and the first create fails with a message about namespaces that mentions nothing you did.
  2. Resource group, storage account, soft delete, shares. Share soft delete is set to 14 days before any data exists, because it cannot protect what was deleted before it was turned on.
  3. Network. Virtual network, the private endpoint subnet, both privatelink DNS zones, and a link from each zone to the network.
  4. Private endpoints. One for the storage account, one for the sync service, each with a DNS zone group that writes the address records. The sync service publishes four names, not one.
  5. DNS Private Resolver. A delegated subnet and an inbound endpoint - the address your own DNS will forward to. The slowest step, around two minutes.
  6. Vault, redundancy, policy, protection. Redundancy and cross-region restore are set before the first protected item, because afterwards they cannot be.
Idempotent means idempotentEvery step checks whether its object already exists. A failed build is fixed and run again - never unpicked. Running it twice changes nothing the second time.

Connect your on-premises servers

The build stops at the edge of Azure. Three steps happen on machines you own, and each one is riskier than anything before it.

1 · The File Sync agent and a server endpoint

Installs the agent, registers the server, then creates the sync group, cloud endpoint and server endpoint. One run, over PowerShell remoting.

.\onprem\Install-AfsServerEndpoint.ps1 `
    -Context .\deploy\deployment-context.json `
    -FileServer fs01.corp.contoso.com `
    -SharePath 'dept-shares=D:\Shares\dept-shares'

Two identities, and why

Registering the server and creating the sync group work under the deployment identity. Creating the cloud endpoint does not. That step grants the Azure File Sync service reader access to your storage account, which is a role assignment - and Contributor is explicitly not allowed to create one. So it runs as the signed-in operator, who must hold Owner, User Access Administrator, or Azure File Sync Administrator on the storage account. The script checks before it tries and prints the exact grant if not.

Requirements on the server

  • Windows Server 2016, 2019, 2022 or 2025
  • .NET Framework 4.7.2 or later
  • The folder on a local NTFS volume - never a mapped drive, never a UNC path, and never the system volume if you want cloud tiering
  • Az.Accounts and Az.StorageSync on the server, because registration only runs there. The script installs them, falling back to copying from your machine when the Gallery is unreachable.
Why the install looks oddThe agent installer closes PowerShell sessions while it runs - which would kill the very remoting session that started it. So it is launched from a scheduled task as SYSTEM and the script polls for the result. That is deliberate, not a workaround.

2 · Point your DNS at the resolver

This has the widest blast radius of anything in the kit. Read this part before running it.

The mistake almost everyone makesA conditional forwarder on privatelink.file.core.windows.net never fires. Clients ask for the public name, and a recursive resolver returns the whole chain - public name, privatelink alias, address - in a single answer. No separate query for the privatelink name is ever issued. The forwarder is created, looks correct, passes a "does the zone exist" check, and does nothing at all. Forward the public zones: file.core.windows.net and afs.azure.net.

The gate

Once the public zone is forwarded, every query for it goes to the resolver. If the resolver cannot be reached, clients get a failure after about eleven seconds for every storage endpoint under that suffix - not just yours. Worse, a resolver that answers wrongly - refused, or a name error because the private zone is not linked to its network - has that answer handed straight back to the client with no fallback at all.

So the script does not test whether the resolver is reachable. It tests whether the resolver returns a private address for a name it should know, and refuses to write anything otherwise.

Replication does not reach everything-ReplicationScope Forest reaches domain controllers that run the DNS role. Not member servers running DNS, not Infoblox, not BIND. Name every resolver your clients actually use, and verify each one.

3 · Domain-join the storage account

Lets people reach the shares with the credentials they already have, so existing NTFS permissions still apply.

.\onprem\Join-AfsStorageAccountToAdDs.ps1 `
    -Context .\deploy\deployment-context.json `
    -OrganizationalUnit 'OU=AzureFiles,DC=corp,DC=contoso,DC=com'

It needs the RSAT Active Directory module, which is the one thing here that wants a local administrator - once:

Install-WindowsFeature RSAT-AD-PowerShell     # elevated, once
A dry run is not inert hereJoin-AzStorageAccount validates in a block that runs even under -WhatIf, and on an unprepared machine it fails with "requires an elevated PowerShell session" - which points at the wrong problem entirely. The script checks the real prerequisites itself, first, so the message you get names the actual cause.

A join on its own lets nobody in

Two more layers decide access, and the most restrictive wins:

  1. Share level. Who may reach the share at all. The default is nobody. Grant one of the SMB share roles, to a hybrid identity - a cloud-only account cannot be used.
  2. File level. The NTFS permissions inside it. Mount once with the account key and set them with icacls. Use net use, not New-PSDrive, or Explorer will not see the drive.

Backup and restore

Three surfaces get confused with each other. Only two of them should ever be backed up.

What to protect, and what never to

SurfaceProtect it withNotes
The migrated virtual machineAzure VM backupTrusted Launch requires the Enhanced policy, and Enhanced cannot go back to Standard.
The Azure file shareAzure Files backupThis is the copy that matters.
The File Sync server endpointNothingIt is a cache. A file-level agent walking tiered files pulls the entire dataset back down.
Never back up a File Sync cacheTiered files are pointers. Any backup product that reads them forces a recall of everything - a bill and an outage at the same time. Back up the share; exclude the server endpoint path.

Which tier restores a single file

This decides whether you can answer "somebody deleted one spreadsheet".

TierRestoresRetention
SnapshotIndividual files and foldersUp to 200 days
Vault-standardThe whole share onlyYears, offsite, immutable

A 60-day requirement fits the snapshot tier comfortably, and that is the tier the build uses.

Proving a restore works

An untested restore is a belief, not a capability. The full loop:

  1. Write a file on the server and let it sync up.
  2. Take a backup, or wait for the scheduled one.
  3. Delete the file.
  4. Restore it to an alternate folder on the same share.
  5. Confirm it syncs back down to the server. This is the step people skip, and it is the one that proves the round trip.
It will look broken for up to a dayChanges written straight to the share are detected once every 24 hours. To see a restored file on the servers now, force detection with Invoke-AzStorageSyncChangeDetection.
The command line cannot do this oneaz backup restore restore-azurefileshare has no source-file option - the CLI can only restore a whole share. Item-level restore needs Restore-AzRecoveryServicesBackupItem in PowerShell.

One thing it will tell you that surprises peopleAzure Files backup traffic is internal to Azure. A vault private endpoint does not apply to it, so there is nothing to route over a private circuit for backup - only for SMB and for sync.

Policy and governance

A different question, with a mature answer already written. This wraps it rather than reinventing it.

The assessor judges this estate. It says nothing about the tenant around it - policy assignments, who can do what, management group shape, locks, Defender coverage. Option 4 runs the Azure Governance Visualizer against the subscription and tenant from your deployment, and puts its report next to the others.

.\Invoke-AfsGovernanceAssessment.ps1 -Context .\deploy\deployment-context.json

Two things it handles for you

  • PowerShell 7. The kit runs on 5.1 deliberately, because the AD DS join needs it. So this shells out to 7 - and looks for it in three places: what you pass, a portable copy in .pwsh7, then the path. No local administrator needed: the same release ships as a plain zip.
  • Reader at the management group. Without it the run finishes and reports almost nothing, which reads like a broken tool rather than a missing role. It checks first, and prints the grant.
Kept separate on purposeThe two reports are not merged. They answer different questions and have different owners; blurring them makes it unclear who has to act on what.

Teardown

The order is not a preference. Each step is refused while the one below it still exists.

Two things that will surprise you

The vault will not delete for 14 daysSoft delete keeps the removed backup data, and a vault holding it cannot be deleted - where a policy sets it to always-on, that cannot be turned off. The teardown detects this, removes every other resource individually instead, and prints the date to come back.
Share snapshots accumulateAzure File Sync takes a share snapshot when a cloud endpoint is created, and never removes it. Repeated build-and-teardown cycles pile them up. List them with az storage share list --include-snapshots.

Cloud tiering changes the risk

A tiered file on disk is a pointer to the cloud copy. Removing a server endpoint while files are still tiered leaves those pointers with nothing behind them. The teardown recalls everything first, and refuses to continue if the recall did not finish.

When it goes wrong

Every message here came from an actual run, not from a specification.

What you seeWhat it meansWhat to do
RequestDisallowedByAzure ... without authenticating through MFAThe session signed in without multi-factor. Reads work, writes do not.az logout, then az login and complete the prompt. More roles will not help.
AuthorizationFailed creating a cloud endpointContributor cannot create role assignments, and a cloud endpoint creates one.Sign in as Owner, User Access Administrator, or Azure File Sync Administrator on the storage account.
-o was unexpected at this time.On Windows az is a batch file, and a closing bracket inside an argument ends one of its blocks early. Any query with a function call trips it.Query plainly and filter afterwards. The kit calls the bundled Python directly to sidestep it.
MissingSubscriptionRegistrationThe subscription has never used that service.Preflight registers the five providers the build needs. By hand: az provider register -n <namespace>.
The endpoint exists but the name still resolves publiclyThe DNS zone group check passed on an empty answer, so no address records were written.Re-run the build; verify with az network private-dns record-set a list.
ScopeLocked deleting the storage accountA lock lives on the resource, not the group. Deleting it by name at group scope reports success and removes nothing.Delete locks by id, and verify afterwards rather than trusting the message.
InUseSubnetCannotBeDeletedChildren before parents: the network is held by an interface, which is held by its private endpoint.The teardown now orders deletes and loops until a pass removes nothing.
"This cmdlet requires an elevated PowerShell session"Almost always means RSAT Active Directory is missing, not that elevation is the real problem.Install-WindowsFeature RSAT-AD-PowerShell, elevated, once.
A run hangs with no output at allSomething is waiting on a prompt that no console can answer.Run it from a real console, or pass -Confirm:$false via -Command. Note that -File silently drops it.
msiexec exit 3010Success. Windows wants a restart to finish releasing the filter driver.Nothing urgent. Restart when convenient.
Sync health is blank just after a buildAzure's telemetry lags roughly fifteen minutes.Read the server first - it knows before Azure does. Or just check whether the files arrived.
usage error: --resource ID | --resource NAMEGit Bash rewrote a resource id into a path. Every id starts with a slash.Run from PowerShell, or set MSYS_NO_PATHCONV=1.

Reading the logs

Every run writes three files into logs/: a readable log, the same events as JSON for tooling, and a console transcript that captures crashes outside the script's own error handling. After a failure, look for the [ERROR] line - it carries the message, the line that threw, and the stack.

LevelShows on screen
QuietWarnings and errors only.
NormalWhat the scripts print.
VerbosePlus every command the kit runs, its result and its timing.
DebugPlus the Azure CLI's own output - hundreds of lines per call.

The file always receives everything; the level only decides what reaches the screen. Each step is timed, and a run ends with a total and the three steps that cost the most. AFS_STEP_PAUSE=2 slows a run down for a demo.

Things that cannot be undone

  • Storage and vault redundancy, and cross-region restore.
  • The Enhanced backup policy for a Trusted Launch machine.
  • A resource group name - Azure has no rename.
  • A server endpoint path.
  • Vault soft delete, where a policy sets it to always-on.
