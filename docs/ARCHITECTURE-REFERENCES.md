## Private connectivity

**[Azure Enterprise Cloud File Share](https://learn.microsoft.com/en-us/azure/architecture/hybrid/azure-files-private)**

- *reference architecture, Microsoft - Azure Architecture Center.* A Microsoft reference architecture for an enterprise hybrid file-sharing solution in which Azure Files and Azure File Sync are reached exclusively over private endpoints from on-premises across ExpressRoute private peering or a VPN tunnel, with Azure private DNS and AD DS authentication.
- **Why it matters here:** This is the closest published Microsoft architecture to Contoso's target state - cloud-tiering file servers on-premises, SMB and sync traffic confined to ExpressRoute, Azure Backup protecting the shares - so it is the canonical diagram, component list and data-flow narrative to anchor the design document against rather than inventing one.
- **Take away:** The design hinges on two independent CNAME chains that must both be resolved privately: Azure Files public name `<account>.file.core.windows.net` CNAMEs to `<account>.privatelink.file.core.windows.net`, while Azure File Sync public name `*.afs.azure.net` CNAMEs to `*.<region>.privatelink.afs.azure.net` - so on-premises DNS must conditionally forward BOTH `file.core.windows.net` and `afs.azure.net` into Azure resolution (a DNS server or DNS Private Resolver in the VNet linked to both private zones); hand-built on-premises A records are named as the brittle fallback.

**[Configure Azure File Sync network endpoints](https://learn.microsoft.com/en-us/azure/storage/file-sync/file-sync-networking-endpoints)**

- *product documentation, Microsoft Learn - Azure Files / Azure File Sync documentation.* The authoritative how-to for creating private endpoints for the storage account and the Storage Sync Service, restricting both public endpoints, and applying the built-in Azure Policy definitions for endpoint compliance.
- **Why it matters here:** It supplies the exact identifiers, PowerShell/CLI commands and - critically - the mandatory ordering for Contoso's cut-over, including the one command that closes the Storage Sync Service and the one setting that must be preserved so Azure File Sync and Azure Backup keep reaching a firewalled storage account.
- **Take away:** Hard cut-over rule, stated as an Important callout: "You must create a private endpoint before disabling access to the public endpoint. If the public endpoint is disabled and there's no private endpoint configured, sync can't work." Use `-GroupId "file"` for the storage account and `-GroupId "Afs"` for the Storage Sync Service (the Afs private endpoint yields four FQDNs and four private IPs: management, syncp, syncs, monitoring); close the Storage Sync Service with `Set-AzStorageSyncService -IncomingTrafficPolicy AllowVirtualNetworksOnly` (Azure CLI cannot set this property, PowerShell or portal only); Azure File Sync does not support service endpoints for the Storage Sync Service - its public endpoint is binary enabled/disabled; and lock the storage account with `-Bypass AzureServices` so trusted first-party services still connect. Also note the current limitation: Storage Sync Services cannot be placed inside a network security perimeter.

**[Azure Private Link in a Hub-and-Spoke Network](https://learn.microsoft.com/en-us/azure/architecture/networking/guide/private-link-hub-spoke-network)**

- *design guide, Microsoft - Azure Architecture Center.* An architecture guide with a decision flowchart for where to place private endpoints in a classic hub-and-spoke topology, covering NVA inspection, NSG control on the private endpoint subnet, routing behaviour and DNS integration.
- **Why it matters here:** Contoso's private endpoints are consumed from on-premises over ExpressRoute rather than from an Azure workload, which is exactly the branch of this guide's decision tree that lands the endpoints in the hub - and it explains the route-propagation behaviour Contoso's network team will see on their ExpressRoute connection once the endpoints exist.
- **Take away:** Decision rule: if a private endpoint is accessed from on-premises, deploy it in the hub in a dedicated subnet - this centralises NSG control, gives a single SNAT rule and a single reusable UDR for NVA steering. Routing fact to plan for: the private endpoint injects a `/32` route with next-hop type `InterfaceEndpoint` that is propagated to every VNet peering and to every VPN/ExpressRoute connection; restrict who may use it with inbound NSG rules on the private endpoint subnet. Cost fact: private-endpoint traffic across a regional VNet peering does not incur peering fees.

**[Manage network policies for private endpoints](https://learn.microsoft.com/en-us/azure/private-link/disable-private-endpoint-network-policy)**

- *product documentation, Microsoft Learn - Azure Private Link documentation.* The how-to that defines the subnet property `privateEndpointNetworkPolicies`, which determines whether network security groups and user-defined routes are actually evaluated for private endpoint traffic in that subnet.
- **Why it matters here:** It closes the single most common silent failure in a locked-down private-endpoint design: Contoso can write a perfect NSG or a firewall-steering UDR on the private endpoint subnet and have it do nothing at all, because the enabling flag is off by default - an auditor-visible control that is not, in fact, enforcing.
- **Take away:** "By default, network policies are disabled for a subnet" - NSGs and UDRs do NOT apply to private endpoint traffic until `privateEndpointNetworkPolicies` is set to `NetworkSecurityGroupEnabled`, `RouteTableEnabled`, or `Enabled` on the private endpoint subnet (Azure CLI only offers the coarse true/false form). And to force private endpoint traffic through a firewall, the UDR prefix must be equal to or more specific than the VNet address space - a 0.0.0.0/0 default route will never override the private endpoint's /32, because longest-prefix match wins.

**[Hub-Spoke Network Topology in Azure](https://learn.microsoft.com/en-us/azure/architecture/networking/architecture/hub-spoke)**

- *reference architecture, Microsoft - Azure Architecture Center.* The customer-managed hub-and-spoke reference architecture, covering the shared cross-premises gateway in the hub, peering and gateway-transit configuration, subnet sizing, spoke-to-spoke routing and throughput scaling.
- **Why it matters here:** Contoso will run one ExpressRoute circuit and one gateway serving multiple spokes, and Azure File Sync recall plus initial-seed traffic is exactly the high-bandwidth on-premises-to-Azure flow that hits the gateway's aggregate throughput ceiling - this document gives both the peering settings and the honest scaling constraints.
- **Take away:** Gateway transit needs three settings, not one: on the hub-to-spoke peering set **Allow gateway transit**, on each spoke-to-hub peering set **Use the remote virtual network's gateway**, and set **Allow forwarded traffic** on all peerings; size `GatewaySubnet` at /26 or larger. Scaling constraint to flag early: a single ExpressRoute gateway caps aggregate throughput, per-TCP-flow throughput and concurrent flows regardless of circuit bandwidth - ExpressRoute FastPath relieves this, but FastPath over VNet peering, UDRs or Private Link requires ExpressRoute Direct, all VNets in the same region, and inspection appliances in the hub VNet (not a spoke).

**[Architecture Best Practices for Azure Files](https://learn.microsoft.com/en-us/azure/well-architected/service-guides/azure-files)**

- *Well-Architected, Microsoft - Azure Well-Architected Framework.* The Well-Architected Framework service guide for Azure Files and Azure File Sync, with per-pillar design checklists and configuration-recommendation tables spanning reliability, security, cost, operations and performance.
- **Why it matters here:** It is the pillar-mapped justification Contoso will want in the design record for why the public endpoint is closed and what the accepted alternative is - and it prices the decision honestly, noting that private endpoints carry standard data-processing charges that a organization budget has to absorb.
- **Take away:** The trap it names explicitly: "A private endpoint doesn't block connections to the public endpoint. You should still disable public network access." Creating the endpoint is only half the control - the `publicNetworkAccess`/firewall change is the other half. Its sanctioned cheaper alternative, if a static private IP is not required, is to restrict public endpoint access to selected virtual networks and IP addresses (service endpoints) instead; and it recommends starting from zero access and adding least privilege incrementally, rather than opening broadly and trimming back.

**[Private Link and DNS Integration at Scale](https://learn.microsoft.com/en-us/azure/cloud-adoption-framework/ready/azure-best-practices/private-link-and-dns-integration-at-scale)**

- *Cloud Adoption Framework, Microsoft - Cloud Adoption Framework for Azure.* CAF landing-zone guidance for operating Private Link at scale: centrally hosted private DNS zones in the connectivity subscription, Azure Policy to deny public endpoints and to auto-register private endpoint DNS records, and cross-premises conditional forwarding.
- **Why it matters here:** Contoso runs Infoblox as its authoritative DNS and IPAM, so this defines the exact seam between the two systems - Infoblox holds conditional forwarders for the public zones and stays authoritative for organization domains, while Azure private DNS zones live centrally and are populated automatically instead of by manual record entry that would drift.
- **Take away:** Adopt the three-policy pattern and never let record creation be manual: (1) Deny storage accounts whose `networkAcls.defaultAction` is not `Deny`; (2) Deny creation of any `Microsoft.Network/privateDnsZones` whose name contains `privatelink.` outside the connectivity subscription, and set "Integrate with private DNS zone = No" when creating endpoints; (3) a DeployIfNotExists policy keyed on the private endpoint's `groupId` that deploys the `privateDnsZoneGroup`, so records follow the endpoint lifecycle and are removed on deletion - its managed identity needs Private DNS Zone Contributor in the zone's subscription. On-premises DNS servers hold one conditional forwarder per public zone pointing at the hub DNS Private Resolver, and that resolver must still be able to resolve public FQDNs or dependent Azure services break.

**[Azure security baseline for Azure File Sync](https://learn.microsoft.com/en-us/security/benchmark/azure/baselines/azure-file-sync-security-baseline)**

- *security baseline, Microsoft - Microsoft cloud security benchmark.* The Microsoft cloud security benchmark baseline for Azure File Sync, enumerating which security features the service supports, which are on by default, and who owns the configuration.
- **Why it matters here:** A US organization needs a control-mapped artefact for its security review, and this one settles an argument that otherwise costs a design cycle: there is no way to place a Storage Sync Service inside Contoso's virtual network, so private endpoints plus the public-access toggle are the only network controls available and both must be deliberately turned on.
- **Take away:** The baseline records "Service can be deployed into customer's virtual network: False" and Virtual Network Integration Supported = **False** - VNet injection is not an option for the Storage Sync Service. Azure Private Link and Disable Public Network Access are both Supported = **True** but Enabled By Default = **False**, Configuration Responsibility = **Customer**: nothing is private until Contoso explicitly makes it so. Note the page carries a banner that it is based on benchmark v1.0, so cite it for the feature-support matrix and control mapping, not for step-by-step configuration.

**[Support Matrix for Azure Files backup by using Azure Backup](https://learn.microsoft.com/en-us/azure/backup/azure-file-share-support-matrix)**

- *limits and quotas, Microsoft Learn - Azure Backup documentation.* The supported-configuration and limits matrix for backing up Azure file shares with Azure Backup, split by snapshot tier and vault-standard tier, covering storage-account support, protection/backup/restore limits and retention.
- **Why it matters here:** This is the document that decides whether Contoso can lock the storage-account firewall all the way down: Azure Backup reaches the storage account as a Microsoft-internal service, so removing the trusted-services bypass in pursuit of a fully private path would silently break Contoso's share backups.
- **Take away:** Snapshot tier is supported only for "Azure Files in storage accounts with Firewall rules that allow Microsoft Azure Services to access storage account" - the trusted-services bypass is a hard dependency, not a convenience, and must be retained when the firewall default action is Deny. For vault-standard tier, "Storage accounts configured with private endpoints are supported. However, a private endpoint on the vault doesn't apply to Azure Files backup scenarios" - do not budget or design a Recovery Services vault private endpoint for file-share backup. Two further gates: the source storage account must keep **Allow storage account key access** enabled, and copy operations from a storage account with a private endpoint into the same virtual network are unsupported because "Azure Trusted Services are allowed, but private endpoints take priority."

**[avm/ptn/network/private-link-private-dns-zones [Network/PrivateLinkPrivateDnsZones]](https://github.com/Azure/bicep-registry-modules/blob/main/avm/ptn/network/private-link-private-dns-zones/README.md)**

- *module registry, Microsoft - Azure Verified Modules (Azure/bicep-registry-modules).* The official Azure Verified Modules Bicep pattern module that deploys the full catalogue of Azure Private Link private DNS zones and links them to the virtual networks that must resolve them.
- **Why it matters here:** It removes the highest-risk manual step in Contoso's build - hand-creating and hand-linking the two zones that Azure Files and Azure File Sync depend on - and it is the module Contoso's platform team should reuse rather than fork, keeping the deployment reproducible for the ExpressRoute-only cut-over and for any DR rebuild.
- **Take away:** Reuse this module instead of authoring zones by hand: its default `privateLinkPrivateDnsZones` set already includes both `privatelink.file.core.windows.net` and `privatelink.afs.azure.net`, `virtualNetworkLinks` (array of objects with `virtualNetworkResourceId`, plus optional `registrationEnabled` and `resolutionPolicy`) links each zone to the hub VNet, and `privateLinkPrivateDnsZonesToExclude` / `additionalPrivateLinkPrivateDnsZonesToInclude` trim or extend the ~70-zone default. Be aware that zones requiring region placeholders are excluded from the default and must be supplied explicitly by the caller.

## Hybrid name resolution

**[Design a Hybrid Domain Name System (DNS) Solution by Using Azure](https://learn.microsoft.com/en-us/azure/architecture/hybrid/hybrid-dns-infra)**

- *reference architecture, Microsoft - Azure Architecture Center.* A reference architecture for bidirectional hybrid DNS, showing on-premises DNS servers, ExpressRoute/VPN, DNS Private Resolver inbound and outbound endpoints, forwarding rulesets, private DNS zones and an Azure Firewall DNS proxy in a hub / shared-services / spoke landing zone.
- **Why it matters here:** It is the only Microsoft architecture that names Infoblox behaviour explicitly, and it settles the global-vs-regional privatelink zone question that decides whether Contoso's Infoblox grid gets deterministic answers when it forwards Azure suffixes over ExpressRoute.
- **Take away:** Use ONE global set of privatelink private DNS zones, not per-region zones: modern BIND (9.4+) and Infoblox choose forwarding targets by lowest measured latency rather than list order, so regional zones make on-premises resolution nondeterministic across regions. Also design for this: a DNS server advances to the next forwarder ONLY when the upstream is unreachable - never on NXDOMAIN or SERVFAIL - so a reachable-but-wrong forwarder is a hard failure, not a failover. Private Resolver and Azure Private DNS are never authoritative (no NS delegation possible); if on-premises requires an authoritative reply for a delegated subdomain, host that zone on DNS VMs instead.

**[Azure Private Endpoint private DNS zone values](https://learn.microsoft.com/en-us/azure/private-link/private-endpoint-dns)**

- *product documentation, Microsoft - Azure Private Link documentation.* The authoritative table mapping every Private Link resource type and subresource to its required privatelink private DNS zone name and its matching public 'DNS zone forwarder' name, published separately for the commercial, US Government and China clouds.
- **Why it matters here:** This is the exact zone inventory this engagement must build and hand to the Infoblox team - privatelink.file.core.windows.net, privatelink.afs.azure.net, blob, queue, privatelink.vaultcore.azure.net, privatelink.{regionCode}.backup.windowsazure.com, privatelink.siterecovery.windowsazure.com and privatelink.prod.migration.windowsazure.com - and it is where you verify the .us suffix variants if any organization workload lands in Azure US Government.
- **Take away:** Zone names must match the documented string character-for-character or the private endpoint's DNS zone group will not auto-generate records ('private DNS zone configurations will only automatically generate if you use the recommended naming scheme'). Two hard boundaries follow: never associate one privatelink zone with two different services' private endpoints - the second registration deletes the first A record; and a privatelink zone linked to a VNet answers NXDOMAIN for public resources of that same type unless you enable Fallback to Internet on the VNet link. The hosts file is listed as an option 'only recommended for testing' - that is the documented status of the hosts-file anti-pattern.

**[Troubleshoot hybrid DNS resolution failures with Azure DNS Private Resolver](https://learn.microsoft.com/en-us/troubleshoot/azure/dns/troubleshoot-azure-dns-private-resolver-hybrid-resolution-failure)**

- *troubleshooting, Microsoft - Azure support / troubleshooting documentation.* A Microsoft support troubleshooter that isolates hybrid DNS failures by direction (inbound vs outbound) and reduces them to four root causes - missing/wrong on-prem forwarder, ruleset linked to the wrong VNet, upstream returning a referral, and MTU/fragmentation - each with dig / Resolve-DnsName checks and a named resolution.
- **Why it matters here:** It is the operational runbook for exactly the failure modes in this principle's scope (public IP answered, NXDOMAIN, stale forwarder, duplicate/competing zone) and it gives the literal Infoblox remediation step, so the consultant can hand Contoso's DNS team an appliance-specific action rather than Azure-only advice.
- **Take away:** Two named root causes carry most incidents. First: an on-premises conditional forwarder pointed at 168.63.129.16 - that address is routable only inside an Azure VNet, so the resolver silently falls back to public DNS and returns the storage account's PUBLIC IP; point it at the inbound endpoint IP instead (for Infoblox/BlueCat: 'create a Forward Zone for the namespace and set the forwarder to $INBOUND_IP'), then flush the cache. Second: 'a forwarding ruleset only takes effect for queries that originate in a VNet to which it is linked' - linking it to the resolver's own hub VNet does nothing for spoke clients. Also a supported-configuration boundary: Private Resolver does not chase NS referrals, so every outbound rule target must be a fully recursive resolver (ra flag set), not an authoritative-only server.

**[Private Link and DNS Integration at Scale](https://learn.microsoft.com/en-us/azure/cloud-adoption-framework/ready/azure-best-practices/private-link-and-dns-integration-at-scale)** (also cited above)

- *Cloud Adoption Framework, Microsoft - Cloud Adoption Framework (Ready / Azure best practices).* CAF guidance for hosting privatelink private DNS zones centrally in the connectivity subscription of a hub-and-spoke landing zone and automating private endpoint DNS record lifecycle with Azure Policy, including worked Deny and DeployIfNotExists policy definitions.
- **Why it matters here:** This is the governance model that keeps a organization's privatelink zones single-instance and self-maintaining - the control that prevents a department or vendor from creating a second privatelink.file.core.windows.net that would shadow the ExpressRoute-only path and produce the duplicate-zone failure mode.
- **Take away:** Deploy two policies together: a Deny on Microsoft.Network/privateDnsZones whose name contains 'privatelink.' (so app teams cannot fork the zone, and must select 'Integrate with private DNS zone = No'), plus a DeployIfNotExists that creates the privateDnsZoneGroup on every private endpoint - and grant that policy's managed identity the Private DNS Zone Contributor role in the connectivity subscription where the zones live. Critical operational rule: if you use the DeployIfNotExists approach, do NOT also configure DNS zone groups in your IaC - the policy owns the DNS integration, and records follow the private endpoint's lifecycle (auto-removed on delete). Prefer the built-in ALZ initiative 'Configure Azure PaaS services to use private DNS zones' over hand-written policies.

**[Configure DNS Forwarding for Azure Files](https://learn.microsoft.com/en-us/azure/storage/files/storage-files-networking-dns)**

- *product documentation, Microsoft - Azure Files documentation.* The Azure Files how-to for making an on-premises client resolve storageaccount.file.core.windows.net to its private endpoint IP across a VPN or ExpressRoute private-peering tunnel, using either DNS server VMs or Azure DNS Private Resolver, with verification commands.
- **Why it matters here:** It is the literal procedure for Contoso's on-premises file clients and Azure File Sync servers, and its cross-tenant warning is a live operational trap the moment Infoblox conditionally forwards the whole core.windows.net suffix to Azure.
- **Take away:** Conditionally forward the PUBLIC storage suffix (core.windows.net) - not privatelink.file.core.windows.net - to the Private Resolver inbound endpoint IP; the resolver needs no configuration of its own because it answers from any private DNS zone linked to its VNet. A correct answer looks like a CNAME to <account>.privatelink.file.core.windows.net plus an A record with the private IP; verify with Clear-DnsClientCache then Resolve-DnsName, and confirm the path with Test-NetConnection -CommonTCPPort SMB. Documented side effect to plan for: forwarding all of core.windows.net breaks access to OTHER tenants' private-endpoint-enabled storage accounts (Azure DNS returns a CNAME with no matching record in your zone); the supported workaround is a cross-tenant private endpoint.

**[DNS for On-Premises and Azure](https://learn.microsoft.com/en-us/azure/cloud-adoption-framework/ready/azure-best-practices/dns-for-on-premises-and-azure-resources)**

- *Cloud Adoption Framework, Microsoft - Cloud Adoption Framework (Ready / Azure best practices).* The CAF landing-zone design area for DNS, listing design considerations and prescriptive recommendations for choosing between Azure Private DNS zones, DNS Private Resolver and existing on-premises DNS infrastructure.
- **Why it matters here:** It supplies the sizing and placement rules that belong in Contoso's landing-zone design document, and it is the citable Microsoft position for keeping the resolver and all privatelink zones in the connectivity subscription rather than scattered across department subscriptions.
- **Take away:** Concrete build constraints to bake into the design: create TWO dedicated subnets for the resolver in the hub VNet in the connectivity subscription - one inbound, one outbound - each a minimum of /28; a resolver supports a maximum of five inbound and five outbound endpoints; and a VNet can be linked to only one private DNS zone with auto-registration enabled. Create all privatelink zones in a global connectivity subscription. Supported-configuration warning: if the resolver shares a VNet with the ExpressRoute gateway, you must ensure public FQDN resolution is still permitted and returns valid answers via a forwarding ruleset rule, because some Azure services depend on resolving public names.

**[Configure Azure File Sync network endpoints](https://learn.microsoft.com/en-us/azure/storage/file-sync/file-sync-networking-endpoints)** (also cited above)

- *product documentation, Microsoft - Azure File Sync documentation.* The how-to for creating private endpoints for both the storage account (file subresource) and the Storage Sync Service, restricting public endpoint access, and the built-in Azure Policy definitions that audit and deploy the matching private DNS records.
- **Why it matters here:** Contoso's caching servers talk to two distinct control planes - the file share over SMB and the Storage Sync Service over afs.azure.net - and missing afs name resolution is the classic reason a registered server shows offline in the portal while SMB mounts keep working.
- **Take away:** A single Storage Sync Service private endpoint produces FOUR hostnames that all must resolve: <name>management, <name>syncp, <name>syncs and <name>monitoring, each at .<region>.afs.azure.net, each CNAMEing into privatelink.afs.azure.net with its own A record. The private DNS zone is described as 'explicitly required for the Azure File Sync agent to access the Storage Sync Service' - optional for creating the endpoint, mandatory for the agent to work. Enforce it with the built-in policies 'Azure File Sync should use private link', 'Configure Azure File Sync with private endpoints' and 'Configure Azure File Sync to use private DNS zones' (which deploys the A record into privatelink.afs.azure.net).

**[DNS security and private name resolution](https://learn.microsoft.com/en-us/azure/networking/design-guide/dns-security)**

- *design guide, Microsoft - Azure networking design guide.* An Azure networking design-guide article with a DNS decision tree, a service/feature comparison table and a set of named patterns (private-endpoint-only, hybrid bidirectional, centralized hub DNS, firewall-mediated, full security stack), pivoted for lift-and-shift, modernize and cross-cloud scenarios.
- **Why it matters here:** It frames the split-brain / preserve-existing-naming problem a organization faces when Infoblox stays authoritative for the corp namespace, and it supplies the DNS-layer security controls and one hard limitation that a public-sector security review will ask about.
- **Take away:** Three design constraints to lift verbatim: inbound and outbound endpoints each require their OWN dedicated subnet delegated to Microsoft.Network/dnsResolvers (plan at least /28) and no other resource may live there; a VNet linked to a forwarding ruleset does NOT need to be peered with the resolver VNet - ruleset links work independently of peering; and Azure DNS does not perform DNSSEC validation for private zones, so if DNSSEC validation is mandated it must happen on the Infoblox/on-premises side. If Azure Firewall is used as DNS proxy, note the cache behaviour (positive up to 1 hour, negative up to 30 minutes) as a stale-record source, and that it will not fall back if all upstream DNS servers fail.

**[Azure Verified Module - DNS Resolver [Microsoft.Network/dnsResolvers]](https://github.com/Azure/bicep-registry-modules/tree/main/avm/res/network/dns-resolver)**

- *module registry, Microsoft - Azure Verified Modules (Azure/bicep-registry-modules).* The official Azure Verified Module (Bicep) for Microsoft.Network/dnsResolvers, deploying the private resolver with its inbound and outbound endpoints, role assignments and resource locks, published to the public Bicep registry.
- **Why it matters here:** It gives Contoso a supported, versioned, reviewable IaC artifact for the resolver instead of portal clicks - which matters for a public-sector change-control trail and for rebuilding the DNS plane identically in a second region or a DR exercise.
- **Take away:** Reuse it as `br/public:avm/res/network/dns-resolver:<version>`; only `name` and `virtualNetworkResourceId` are required, with `inboundEndpoints` / `outboundEndpoints` as arrays. Plan for TWO modules, not one: forwarding rulesets, rules and VNet links are a separate AVM module, `br/public:avm/res/network/dns-forwarding-ruleset:<version>`, whose required `dnsForwardingRulesetOutboundEndpointResourceIds` array wires it to the resolver's outbound endpoint, with `forwardingRules` and `virtualNetworkLinks` as parameters - that second module is where you encode the per-spoke ruleset links that the troubleshooting guide identifies as the most commonly omitted step.

## Storage account security baseline

**[Azure Enterprise Cloud File Share](https://learn.microsoft.com/en-us/azure/architecture/hybrid/azure-files-private)** (also cited above)

- *reference architecture, Microsoft - Azure Architecture Center.* Microsoft's reference architecture for an enterprise hybrid file-share estate built on Azure Files, Azure File Sync with cloud tiering, private endpoints, Azure private DNS zones and Azure Backup, reached from on-premises over ExpressRoute private peering or a site-to-site VPN.
- **Why it matters here:** This is Contoso's target state almost line for line - File Sync caching servers on-premises, SMB and sync traffic confined to ExpressRoute private peering, Azure Backup on the shares - so it is the authoritative picture that every storage-account hardening decision has to serve, and it is the diagram to put in front of the customer.
- **Take away:** It fixes private-endpoint-plus-restricted-public-access as the default posture and spells out the DNS consequence that breaks deployments: `<account>.file.core.windows.net` CNAMEs to `<account>.privatelink.file.core.windows.net`, and File Sync CNAMEs to `<region>.privatelink.afs.azure.net`. Infoblox must therefore hold either conditional forwarders for `file.core.windows.net` and `afs.azure.net` pointed at a resolver in the Azure VNet, or authoritative `privatelink.*` zones with A records for the private endpoint IPs - otherwise every on-premises client resolves the public endpoint and is then denied by the storage firewall.

**[Architecture Best Practices for Azure Files](https://learn.microsoft.com/en-us/azure/well-architected/service-guides/azure-files)** (also cited above)

- *Well-Architected, Microsoft - Azure Well-Architected Framework.* The Well-Architected Framework service guide for Azure Files and Azure File Sync, with separate security design checklists and configuration-recommendation tables for SMB and NFS shares across all five pillars, plus a section naming the Azure Policy audits that back the recommendations.
- **Why it matters here:** It is the only Microsoft source that converts the storage-account security settings into a ranked recommendation/benefit table a consultant can hand to a organization architecture review board, and it keeps SMB requirements distinct from NFS ones - which matters because Contoso's shares are SMB-only and inherit the identity-based access model NFS cannot use.
- **Take away:** Lift the counter-intuitive rule: do NOT strip NTLMv2 from the account's SMB security settings even though that is the switch which blocks storage-account-key mounts - Microsoft warns that "administrators might still need to use the storage account key for some tasks." Alongside it, keep SMB and NFS shares in separate storage accounts, apply a Resource Manager lock on the account to prevent deletion, enable share soft delete with a minimum seven-day retention, and budget for Defender for Storage carefully because transaction-heavy file shares make it expensive and it provides no antivirus for Azure file shares.

**[Azure security baseline for Storage](https://learn.microsoft.com/en-us/security/benchmark/azure/baselines/storage-security-baseline)**

- *security baseline, Microsoft - Microsoft cloud security benchmark.* The Microsoft cloud security benchmark baseline for Azure Storage, enumerating per control family (NS-1/NS-2 network, IM-1/IM-3/IM-7/IM-8 identity, PA-7 privileged access, DP-3/DP-4/DP-5/DP-6 data protection, AM-2 asset management, LT-1/LT-4 logging, BR-1 backup) whether each feature is supported, whether it is enabled by default, and who owns configuring it.
- **Why it matters here:** A organization security office will expect the baseline mapped to a recognised benchmark rather than to a consultant's opinion, and this is the document Microsoft Defender for Cloud's Regulatory Compliance blade scores the storage account against - making it the evidence artifact for the security-review gate.
- **Take away:** Use the "Enabled By Default / Configuration Responsibility" columns directly as the gap list: private endpoints (NS-2), disable public network access (NS-2), customer-managed keys (DP-5), Defender for Storage (LT-1) and resource logs to Log Analytics (LT-4) are every one of them *supported, NOT enabled by default, customer responsibility*. Note honestly that the page carries a Microsoft banner stating it tracks MCSB v1.0 and may contain outdated guidance - cite it for the control mapping and compliance framing, and pair it with the current Azure Files WAF service guide for the actual configuration values.

**[How do I apply Zero Trust principles to storage in Azure?](https://learn.microsoft.com/en-us/security/zero-trust/azure-infrastructure-storage)**

- *design guide, Microsoft - Zero Trust guidance.* Microsoft's Zero Trust implementation guide for Azure Storage, walking four steps - protect data at rest, in transit and in use; verify users and control access with least-privilege RBAC; logically segregate critical data with network controls; and use Defender for Storage for automated threat detection - each mapped back to the verify-explicitly / least-privilege / assume-breach principles.
- **Why it matters here:** US public-sector customers increasingly write Zero Trust language directly into security policy and grant conditions, and this gives the consultant Microsoft's own wording for how each storage-account toggle satisfies a named Zero Trust principle, plus the resource-group isolation and PIM pattern a organization needs for separation of duties over the file estate.
- **Take away:** The hard sequencing constraint to design for: infrastructure (double) encryption, customer-managed keys, and the copy-operation scope are chosen **at storage-account creation and cannot be changed afterwards**. **[SMB File Shares in Azure Files](https://learn.microsoft.com/en-us/azure/storage/files/files-smb-protocol)**

- *product documentation, Microsoft - Azure Files documentation.* The definitive product reference for SMB Azure file shares, containing the Windows-version-to-SMB-capability support matrix and the account-level SMB security settings - allowed protocol versions, channel encryption algorithms, authentication methods, Kerberos ticket encryption - plus the newer per-protocol "Require Encryption in Transit for SMB" control.
- **Why it matters here:** These are Contoso's most dangerous settings: they are storage-account-wide, apply to every classic share in the account, are evaluated at SMB session setup, and a failed negotiation surfaces to the help desk only as an opaque STATUS_ACCESS_DENIED on mount - so the hardening level must be chosen against the actual Windows build inventory, not against an aspiration.
- **Take away:** The supported-configuration boundary: AES-256-GCM channel encryption exists only on Windows 11 and Windows Server 2022 and later, and selecting it exclusively additionally requires running `Set-SmbClientConfiguration -EncryptionCiphers "AES_256_GCM"` on every client. The defensible organization baseline is `--versions SMB3.1.1 --auth-methods Kerberos --kerb-ticket-encryption AES-256`, but leave AES-128-GCM enabled alongside AES-256-GCM until the Windows 10 / Server 2019 estate is retired. Also critical: "Require Encryption in Transit for SMB" now governs SMB independently of the account's "Secure transfer required" flag (which now covers only REST/HTTPS), and it defaults ON only for accounts created in the portal - accounts created by CLI, PowerShell, or IaC come up "Not selected", so set it explicitly.

**[Guidelines & limitations: Azure Storage firewall](https://learn.microsoft.com/en-us/azure/storage/common/storage-network-security-limitations)**

- *limits and quotas, Microsoft - Azure Storage documentation.* The restrictions-and-considerations companion to the Azure Storage firewall documentation, defining what network rules do and do not cover, which address ranges and request origins they cannot express, and the precedence order between trusted services, resource instances and the default action.
- **Why it matters here:** With ExpressRoute-only file traffic, Contoso's instinct will be to allowlist their on-premises RFC 1918 ranges in the storage firewall; this is the page that proves that cannot work and forces the private-endpoint design, and it also names the IaC defect that would otherwise leave the account permanently flagged in Defender for Cloud.
- **Take away:** Three constraints to design around. (1) IP network rules accept **public internet addresses only** - RFC 1918 ranges (10.x, 172.16-172.31.x, 192.168.x) are rejected, /31 and /32 prefixes are unsupported, IPv4 only, and IP rules have no effect at all on requests originating in the same Azure region - so ExpressRoute private-peering sources can be admitted only via private endpoints or virtual-network rules. (2) Firewall rules apply to the **data plane only** and are enforced on SMB as well as REST, but control-plane operations bypass them entirely. (3) Setting `publicNetworkAccess = Disabled` from a template leaves `defaultAction` at `Allow`, and previously configured resource-instance rules and the "Allow Azure services on the trusted services list" exception **remain in effect** - so set `defaultAction: 'Deny'` explicitly in the module parameters, or Defender for Storage and Advisor will keep raising the finding.

**[Prevent authorization with Shared Key](https://learn.microsoft.com/en-us/azure/storage/common/shared-key-authorization-prevent)**

- *product documentation, Microsoft - Azure Storage documentation.* The Detect-Remediate-Audit-Govern procedure for setting `AllowSharedKeyAccess = false`, covering how each SAS type behaves afterwards, which Azure tools and services break, how to measure shared-key usage before flipping the switch, and how to move the governing Azure Policy from Audit to Deny.
- **Why it matters here:** "Disable shared key access" appears on essentially every organization hardening checklist and CIS-style benchmark, and this is the page that states plainly it is the wrong control for a file-share account - applying it blindly would make Contoso's Azure Files data unreachable from the portal and from any REST or SAS-based tooling, including parts of the backup and reporting chain.
- **Take away:** Microsoft's own decision rule for exactly this case: "**Don't apply this setting to storage accounts that support Azure Files workloads**" - the only alternatives being to grant the Entra file-data RBAC roles first, or to move Files data to a separate account. Before touching it, run the Resource Graph query `resources | where type =~ 'Microsoft.Storage/storageAccounts' | extend allowSharedKeyAccess = parse_json(properties).allowSharedKeyAccess`, assign the built-in **Storage accounts should prevent shared key access** policy in **Audit** mode, and filter the Transactions metric by `Authentication = Account Key / SAS` (and the `StorageBlobLogs` `AuthenticationType in ("AccountKey","SAS")` query) to identify who still depends on the key. Note that only a *user delegation* SAS survives the change; service SAS and account SAS are denied outright, and disallowing shared key is a hard prerequisite if Contoso ever wants Entra Conditional Access to apply to the storage account.

**[Built-in policy definitions for Azure Storage](https://learn.microsoft.com/en-us/azure/storage/common/policy-reference)**

- *product documentation, Microsoft - Azure Storage documentation.* The generated catalogue of Azure Policy built-in definitions in the Microsoft.Storage namespace, each with its name, description, effects and definition ID, spanning audit (Audit/Deny) and remediation (DeployIfNotExists / Modify) variants.
- **Why it matters here:** Contoso will want this baseline enforced continuously rather than documented once, and this is the source list for the storage initiative a landing-zone policy assignment would carry - it is also the only place in this set where the account-key lifecycle control and the File Sync private-endpoint guardrails actually exist as enforceable definitions.
- **Take away:** The named built-ins that map one-to-one onto this baseline, ready to assemble into a organization initiative: *Secure transfer to storage accounts should be enabled*; *Storage accounts should have the specified minimum TLS version*; *Storage accounts should disable public network access*; *Storage accounts should restrict network access using virtual network rules*; *Storage Accounts should restrict network access through network ACL bypass configuration only*; *Storage accounts should use private link*; *Storage accounts should use customer-managed key for encryption*; *Storage accounts should have infrastructure encryption*; **Storage account keys should not be expired** (the key-lifecycle/rotation control); *Storage accounts should have shared access signature (SAS) policies configured*; *Configure diagnostic settings for File Services to Log Analytics workspace*; and *Azure File Sync should use private link* / *Configure Azure File Sync with private endpoints*. Deliberately omit *Storage accounts should prevent shared key access* from the enforced set for the Files account per the shared-key guidance above. Assign the `Configure*` DeployIfNotExists variants only after the corresponding audit variants report clean.

**[Storage Accounts `[Microsoft.Storage/storageAccounts]` - Azure Verified Module](https://raw.githubusercontent.com/Azure/bicep-registry-modules/main/avm/res/storage/storage-account/README.md)**

- *module registry, Microsoft - Azure Verified Modules (Azure/bicep-registry-modules).* The Azure Verified Module for storage accounts, published to the Microsoft public Bicep registry as `br/public:avm/res/storage/storage-account`, shipping with 16 worked deployment examples including a WAF-aligned configuration, and exposing the full security surface as typed parameters and child resources.

- **Take away:** Deploy with a pinned version - `br/public:avm/res/storage/storage-account:<version>` - and drive the entire baseline through module parameters rather than portal clicks: `networkAcls` (`defaultAction: 'Deny'` plus `bypass`, `ipRules`, `virtualNetworkRules`, `resourceAccessRules`), `publicNetworkAccess`, `allowSharedKeyAccess`, `minimumTlsVersion`, `allowBlobPublicAccess: false`, `customerManagedKey` (Key Vault or Managed HSM, system- or user-assigned identity), `requireInfrastructureEncryption`, `fileServices` (share soft-delete retention and the SMB protocol settings), `privateEndpoints`, `diagnosticSettings`, `lock` and `roleAssignments`. The published examples already demonstrate `allowBlobPublicAccess: false` with `"defaultAction": "Deny"` and explicit allow rules, so the secure posture is the starting template rather than an override.

## Identity and access

**[Azure Files Accessed from On-Premises and Secured by AD DS in a Private Network](https://learn.microsoft.com/en-us/azure/architecture/example-scenario/hybrid/azure-files-on-premises-authentication)**

- *reference architecture, Microsoft Learn - Azure Architecture Center.* A Microsoft-maintained example scenario that assembles the full pattern for on-premises users reaching an Azure file share privately: Entra Connect sync, a private endpoint in a dedicated subnet, ExpressRoute or VPN, a DNS proxy/conditional forwarder, and on-premises AD DS as the authentication authority.
- **Why it matters here:** This is the closest published Microsoft architecture to Contoso's target state - ExpressRoute-only file traffic, private endpoint, on-premises AD DS retained as the identity source, and on-premises DNS conditionally forwarding to resolve the share FQDN - so it is the diagram and component list the consultant can cite as the sanctioned reference rather than a bespoke design.
- **Take away:** The workflow fixes the enablement order and separates identity from network: sync AD DS to Entra ID first, then enable AD DS authentication on the storage account as a four-step process (domain-join the account, assign share-level RBAC, configure Windows ACLs, mount), while the private endpoint plus a conditional forwarder from the on-premises DNS to Azure DNS is what makes the share resolvable at all. Also lift its performance constraint into the storage-account design: no more than one highly active file share per storage account, and never co-locate databases or blobs with file shares.

**[Architecture Best Practices for Azure Files](https://learn.microsoft.com/en-us/azure/well-architected/service-guides/azure-files)** (also cited above)

- *Well-Architected, Microsoft Learn - Azure Well-Architected Framework.* The WAF service guide for Azure Files and Azure File Sync, with a Security pillar checklist and configuration-recommendation table split by SMB versus NFS, plus the Azure Policy definitions that audit those controls.
- **Why it matters here:** It gives Contoso's security reviewers a pillar-mapped, auditable statement of the identity posture - identity-based auth over account keys, AES-256 Kerberos, minimum TLS and SMB versions - and names the Azure Policy definitions (shared key authorization disabled, public network access disabled, File Sync private endpoints with private DNS zones) that can be attached to the subscription as guardrails.
- **Take away:** The explicit recommendation is to use identity-based authentication with AES-256 Kerberos ticket encryption, and to minimize storage account keys by using the Windows permission model for SMB admin to take ownership and set ACLs without the key. But note the supported-configuration boundary it draws: you *can* fully disallow account-key access to a share by removing NTLMv2 from the share's SMB security settings, and Microsoft advises generally not to, because administrators still need the key for some tasks - so plan a key-custody process in Key Vault instead of a hard block.

**[Hybrid identity with Active Directory and Microsoft Entra ID in Azure landing zones](https://learn.microsoft.com/en-us/azure/cloud-adoption-framework/ready/landing-zone/design-area/identity-access-active-directory-hybrid-identity)**

- *Cloud Adoption Framework, Microsoft Learn - Cloud Adoption Framework.* The CAF landing-zone design-area article governing hybrid identity: when to extend AD DS into Azure versus use Entra Domain Services versus stay cloud-only, where identity infrastructure must live in the landing-zone hierarchy, and how to protect it.
- **Why it matters here:** It settles the governance questions a Contoso will be asked in review - who owns identity (the platform team, in a dedicated Identity subscription), whether new domain controllers are needed in Azure at all, and how AD sites must be extended so authentication stays local - which is the layer above the Azure Files product decisions and the one an auditor will ask about.
- **Take away:** The decision rule to lift verbatim: "Consider using Kerberos authentication for Microsoft Entra ID instead of deploying domain controllers in the cloud if a Windows user requires Kerberos for Azure Files file shares" - i.e. do not stand up Azure-hosted DCs just to serve file shares. Two more rules that bind here: place domain controllers, Entra Connect servers, and any Arc resources that manage identity services in the Identity platform subscription with restricted RBAC (Contributor/Owner on a DC VM is effectively domain admin), and create an AD site and subnet object per Azure region so the DC locator directs authentication to the nearest controller.

**[Overview - Azure Files Identity-Based Authentication](https://learn.microsoft.com/en-us/azure/storage/files/storage-files-active-directory-overview)**

- *product documentation, Microsoft Learn.* The canonical overview of the three identity sources Azure Files supports over SMB - on-premises AD DS, Microsoft Entra Domain Services, and Microsoft Entra Kerberos - including the Kerberos ticket flow and an explicit set of guidelines for choosing between them.
- **Why it matters here:** This is the authentication decision tree for the engagement, and it is where the Entra Kerberos alternative is defined: it lets Contoso keep the AD DS path today while documenting the exit ramp, and it states the migration path if Contoso later moves to cloud-only identities.
- **Take away:** The hard constraint that shapes the storage-account topology: **you can use only one identity source per storage account, and it applies to every file share in that account**. Shares with different authentication requirements must therefore be split across separate storage accounts. The choice rule: pick AD DS only when clients are domain-joined or have unimpeded network connectivity to domain controllers; pick Entra Kerberos when some clients lack that connectivity, when authenticating cloud-only identities, or when macOS clients are in scope. A storage account can be migrated from AD DS to Entra Kerberos later, but only by disabling one source before enabling the other.

**[Enable AD DS Authentication for Azure Files](https://learn.microsoft.com/en-us/azure/storage/files/storage-files-identity-ad-ds-enable)**

- *product documentation, Microsoft Learn.* The procedural authority for domain-joining the storage account, covering both the AzFilesHybrid module path (Join-AzStorageAccount) and the manual path, plus AES-256 enablement and the domain-properties set on the storage account.
- **Why it matters here:** It defines the AD object Contoso's directory team must actually create and then own for the life of the service - the computer object, its SPN, its encryption type, and its password - and it names the minimum Azure roles the operator running the join needs, which is the concrete least-privilege ask for the change ticket.
- **Take away:** Four specifics to carry into the runbook. (1) The AD object must carry SPN `cifs/<storage-account-name>.file.core.windows.net`; for a User/service-logon account the UPN must be set to match the SPN or AES-256 Kerberos fails with error 1396 / KRB_AP_ERR_MODIFIED. (2) AES-256 requires a computer or service logon account and write access to `msDS-SupportedEncryptionTypes`; set it with `Set-ADComputer -KerberosEncryptionType "AES256"`. (3) The object's password *is* the storage account kerb1 key and must be rotated before the OU's maximum password age - place the object in a dedicated OU with password expiration disabled and schedule the refresh, because expiry silently breaks all SMB access. (4) Least privilege for the join operator is only Reader on the resource group plus Contributor on the storage account in Azure, plus AD rights to create the object - not Owner. Note also the July 2026 Windows Server update flipping the AD DS default Kerberos encryption type from RC4 to AES-256.

**[Assign Share-Level Permissions for Azure Files](https://learn.microsoft.com/en-us/azure/storage/files/storage-files-identity-assign-share-level-permissions)**

- *product documentation, Microsoft Learn.* The definitive reference for the share-level Azure RBAC layer: the seven built-in Azure Files data roles, the default share-level permission, how the two combine, and the group-based path for AD DS users who are not individually synced to Entra ID.
- **Why it matters here:** This is the single most on-scope document for the engagement - it resolves how share-level RBAC and NTFS ACLs coexist, and it supplies the answer for Contoso's inevitable population of service accounts, gMSAs, computer accounts, and staff who will not be synced individually to Entra ID.
- **Take away:** Three rules that change the design. (1) **Group-based path:** only the AD DS *group* needs to sync to Entra ID - the on-premises DC issues a Kerberos ticket containing all group SIDs, Azure Files reads those SIDs and applies matching RBAC assignments, so non-synced users get access through synced group membership even though they never appear as members in the Entra admin center. (2) **Higher permission always wins** when a default share-level permission and a specific assignment both apply - a permissive default silently overrides a restrictive per-user grant, so keep the default at its initial value of *None* unless deliberately used. (3) Computer accounts, sMSAs and gMSAs have no Entra identity and therefore *cannot* be RBAC-assigned at all; they can only reach a share via the default share-level permission. Also treat `Storage File Data Privileged Contributor`/`Privileged Reader` as break-glass - they override existing ACLs - and scope all assignments to the share resource ID, never the subscription.

**[How to Use Managed Identities with Azure File Sync](https://learn.microsoft.com/en-us/azure/storage/file-sync/file-sync-managed-identities)**

- *product documentation, Microsoft Learn.* The guide to replacing shared-key authentication in Azure File Sync with system-assigned managed identities across all three flows - Storage Sync Service to file share, registered server to file share, and registered server to Storage Sync Service - including the exact roles the platform grants on your behalf.
- **Why it matters here:** Contoso's cached on-premises Windows servers are the reason this matters: because they are outside Azure they must be Arc-enabled to hold a system-assigned identity at all, which turns Azure Arc onboarding from an optional nicety into a prerequisite of the keyless File Sync design.
- **Take away:** Enabling this grants, automatically: **Storage Account Contributor** to the Storage Sync Service on each storage account, **Storage File Data Privileged Contributor** to the Storage Sync Service on each file share, and **Storage File Data Privileged Contributor** to every registered server's identity on the shares - an ACL-overriding role, so review the blast radius before enabling. Boundaries to plan around: agent v20.0.0.0+; non-Azure servers must be Arc-enabled; cross-tenant topologies are unsupported (sync service, server resource, identity, and RBAC assignments must share one Entra tenant); a newly registered server does **not** inherit the configuration - rerun `Set-AzStorageSyncServiceIdentity` or it silently keeps using shared keys; and allow up to 15 minutes for cutover. For the operator, use the documented least-privilege pattern: assign **Azure File Sync Administrator** with an ABAC condition restricting it to granting only Reader and Data Access, Storage File Data Privileged Contributor, and Storage Account Contributor.

**[Manage Backups with Azure role-based access control](https://learn.microsoft.com/en-us/azure/backup/backup-rbac-rs-vault)**

- *product documentation, Microsoft Learn.* The Azure Backup RBAC reference defining Backup Contributor, Backup Operator and Backup Reader, with per-workload tables of the minimum role required for each management operation - including a dedicated table for Azure File Share backup.
- **Why it matters here:** It converts Contoso's separation-of-duties requirement into concrete grants for the team protecting the file shares, and it draws the line that matters for a public-sector ransomware posture: the operator who takes and restores backups should not be the one who can stop protection or delete a policy.
- **Take away:** The Azure File Share table is the citation. Enable backup = **Backup Contributor** on the Recovery Services vault **plus Storage Account Contributor** on the storage account (plus subscription Contributor if configuring from the file share blade). On-demand backup and restore = **Backup Operator** on the vault; a full share restore additionally needs **Storage Account Backup Contributor** on both source and target storage accounts, while individual-file restore needs **Storage Account Contributor**. Stop protection and unregistering the storage account require **Backup Contributor** - so give day-to-day staff Backup Operator only, and reserve Backup Contributor for a small change-controlled group. Gotcha worth pre-empting: configuring backup from the file share blade with only resource-group-level contributor requires a custom role carrying `microsoft.recoveryservices/Locations/backupStatus/action` at subscription scope.

**[Azure security baseline for Storage](https://learn.microsoft.com/en-us/security/benchmark/azure/baselines/storage-security-baseline)** (also cited above)

- *security baseline, Microsoft Learn - Microsoft cloud security benchmark.* The Microsoft cloud security benchmark baseline for Azure Storage, enumerating per-control support and configuration responsibility across Identity Management (IM-1, IM-3, IM-7, IM-8), Privileged Access (PA-1, PA-7, PA-8), and Data Protection - monitorable through Defender for Cloud's Regulatory Compliance view. Note it carries a banner stating it is based on MCSB v1.0 and may contain outdated guidance, so cite it as a control-mapping artifact and verify specifics against current product docs.
- **Why it matters here:** A US organization will need to map this deployment to a control framework for its own compliance and audit reporting, and this is the artifact that expresses the identity posture as named, individually attestable controls with a stated customer-versus-Microsoft responsibility split.
- **Take away:** The highest-value control is **IM-7**: disallow Shared Key authorization on the storage account so that data-plane access is Entra-only and therefore becomes subject to Entra Conditional Access - this is what turns "we prefer identity-based auth" into an enforceable boundary rather than a convention, and it should be paired with the WAF caveat about administrators still needing key access for some SMB tasks. Alongside it: IM-3 directs managed identities over service principals (the File Sync path), PA-7 makes data-plane RBAC a customer responsibility that is *not* on by default, and PA-1 confirms Storage has no local admin account - so every privileged path is an Azure role assignment you can enumerate and review.

## File Sync topology and cloud tiering

**[Hybrid file services](https://learn.microsoft.com/en-us/azure/architecture/hybrid/hybrid-file-services)**

- *reference architecture, Microsoft Azure Architecture Center.* The Azure Architecture Center reference architecture for extending file services across on-premises and Azure using Azure File Sync and Azure Files, covering Storage Sync Service placement, sync group and endpoint configuration, the two agent components (FileSyncSvc.exe and StorageSync.sys), the Windows Server support matrix, and firewall/ExpressRoute/proxy topology options.
- **Why it matters here:** This is the baseline topology diagram the Contoso design should be drawn against - it is the one Microsoft-published architecture that shows the organization's exact shape (domain-joined on-premises file servers caching Azure file shares, ACLs syncing with the data, sync and file traffic tunnelled over ExpressRoute) rather than a direct-mount pattern.
- **Take away:** Provision as few Storage Sync Services as possible and map Azure file shares one-to-one with Windows file shares, making the server endpoint path match the Windows share path: a server or cluster can register to only ONE Storage Sync Service, and servers in different Storage Sync Services can never sync with each other, so that boundary is a permanent partition of the organization's namespace chosen at day one. Also map file shares one-to-one with storage accounts where possible, since IOPS is a storage-account-level scale target shared across shares.

**[Azure Enterprise Cloud File Share](https://learn.microsoft.com/en-us/azure/architecture/hybrid/azure-files-private)** (also cited above)

- *reference architecture, Microsoft Azure Architecture Center.* A reference architecture for a private-only enterprise cloud file share built from Azure Files, Azure File Sync with cloud tiering, private endpoints, Azure private DNS zones, on-premises DNS conditional forwarders, ExpressRoute private peering, and Azure Backup, with the full DNS resolution and traffic flow spelled out step by step.
- **Why it matters here:** This is the precise pattern for the organization's constraint set - ExpressRoute-only file and sync traffic, Infoblox as the on-premises DNS authority, and Azure Backup protecting the shares - and it shows exactly which DNS records Infoblox must carry versus which must be forwarded into Azure.
- **Take away:** Private connectivity requires TWO private endpoints (one for the storage account, one for the Storage Sync Service) plus DNS work, because the public FQDNs are CNAMEs into the privatelink domains: `*.afs.azure.net` redirects to `*.<region>.privatelink.afs.azure.net` and `<name>.file.core.windows.net` redirects to `<name>.privatelink.file.core.windows.net`. Infoblox must either conditionally forward `afs.azure.net` and `file.core.windows.net` to an Azure-side resolver (DNS Private Resolver or a VNet DNS server linked to the private zones), or host those privatelink zones locally with A records - DNS, not routing, is what actually forces traffic down the ExpressRoute circuit.

**[Architecture Best Practices for Azure Files](https://learn.microsoft.com/en-us/azure/well-architected/service-guides/azure-files)** (also cited above)

- *Well-Architected, Microsoft Azure Well-Architected Framework.* The Well-Architected Framework service guide for Azure Files and Azure File Sync, giving pillar-mapped design checklists and configuration recommendation tables across Reliability, Security, Cost Optimization, Operational Excellence, and Performance Efficiency, plus the list of auditable Azure Policy definitions.
- **Why it matters here:** It supplies the defensible review lens a organization deliverable needs - redundancy selection, vaulted Azure Backup for ransomware protection, and the governance control that proves the ExpressRoute-only posture is actually enforced rather than merely designed.
- **Take away:** Two things to lift: (1) there is a built-in Azure Policy that audits whether *Azure File Sync is configured with private endpoints to use private DNS zones* - make that the enforcement guardrail for the private-connectivity requirement instead of relying on a build document; and (2) Azure File Sync takes share-level and file-level snapshots as part of normal operation, so File Sync adds snapshot cost to the Azure Files bill on top of whatever Azure Backup retains - budget both. Note also that only standard SMB accounts support GRS/GZRS, which constrains the redundancy choice for the organization's shares.

**[Plan an Azure File Sync deployment](https://learn.microsoft.com/en-us/azure/storage/file-sync/file-sync-planning)**

- *product documentation, Microsoft Learn (Azure Storage documentation).* The canonical planning document for Azure File Sync: the Storage Sync Service / registered server / sync group / cloud endpoint / server endpoint object model and its cardinality, a decision table of share-to-Azure-file-share mapping scenarios marked supported or unsupported, the cloud tiering free-space arithmetic, failover clustering support, Data Deduplication interoperability, DFS-N and DFS-R constraints, antivirus, and backup guidance.
- **Why it matters here:** This is the document that decides how the organization's existing shares and volumes are allowed to land in Azure and which of its incumbent server-side products (DFS-R, deduplication, antivirus, an on-premises backup agent) can legally coexist with a tiered server endpoint.
- **Take away:** The mapping rule is hard and non-negotiable: a cloud endpoint (Azure file share) can be configured in only ONE sync group, and a sync group supports only one server endpoint per registered server - so consolidating multiple on-premises shares or volumes into a single Azure file share is explicitly unsupported, forcing 1:1 mapping with a cap of 30 Azure file shares per server or cluster. For coexistence: DFS-R and File Sync can run side by side only if cloud tiering is DISABLED on volumes holding DFS-R replicated folders, no server endpoint sits on a read-only DFS-R folder, and at most one server endpoint overlaps a DFS-R location; DFS-N is fully supported. No other HSM product may be used alongside cloud tiering. If an on-premises backup product is retained, run it on a sync-group member with cloud tiering disabled and no tiered files, and prefer file-level restore (volume-level restore will not replace newer versions in the Azure file share).

**[Understand Azure File Sync Cloud Tiering](https://learn.microsoft.com/en-us/azure/storage/file-sync/file-sync-cloud-tiering-overview)**

- *product documentation, Microsoft Learn (Azure Storage documentation).* The conceptual reference for cloud tiering: how the namespace is split from file content, what a reparse point is and which NTFS attributes a tiered file carries, how the heat store and heatmap rank files, the volume free space and date policies, Windows Server deduplication support, proactive recall, partial recall, and low disk space mode with its threshold formula.
- **Why it matters here:** It defines the on-premises cache mechanics the organization's caching servers will actually run, and names the file attribute that every antivirus, backup, indexing, and classification agent in the organization estate must be verified to honour before tiering is enabled - the single largest cause of recall storms and unplanned ExpressRoute egress.
- **Take away:** A tiered file's heat position is MAX(Last Access Time, Last Modified Time, Creation Time), tracked independently by storagesync.sys - do NOT enable the NTFS last-access-time feature to help it (explicitly warned against for performance). Two operational cliffs to instrument: Azure File Sync reserves 10% of total memory for persisting recalls, and above 60% use of that reserve recalls stop being persisted at all (causing repeat egress, I/O degradation, and hangs); and the volume enters low disk space mode below MIN(10% of volume size, volume free space policy in GiB, 20 GiB), after which recalls likewise are not persisted to disk. Alert on Telemetry Event ID 19000 with IsLowDiskMode=true rather than waiting for user-reported slowness.

**[Choose Azure File Sync Cloud Tiering Policies](https://learn.microsoft.com/en-us/azure/storage/file-sync/file-sync-choose-cloud-tiering-policies)**

- *design guide, Microsoft Learn (Azure Storage documentation).* Microsoft's prescriptive guidance for selecting and tuning the two cloud tiering policies, including recommended starting values, a churn-based method for sizing how much data to keep local, the minimum tierable file size table by NTFS cluster size, the effects of over-aggressive tiering, and the supported-configuration limits for tiering.
- **Why it matters here:** It gives the organization a defensible, citable starting policy per caching server and the arithmetic to size each server's local volume from actual churn - the difference between a cache that serves the organization's users at LAN speed and one that trickles every open back over the ExpressRoute circuit.
- **Take away:** Start with the date policy DISABLED and volume free space at 10-20% (20% is the recommended default), then tune from measured churn: if roughly 10% of a 1 TiB dataset is active each month, keep ~100 GiB local and add a buffer for peak churn. Three supported-configuration boundaries to check before design sign-off: cloud tiering is NOT supported on the Windows system volume; the minimum tierable file size is 2x the volume cluster size with an 8 KiB floor (so a 64 KiB-cluster volume cannot tier anything below 128 KiB - a real trap on large, non-default-formatted organization volumes); and FSRM quotas must be applied at folder level, never at the volume root, or a hard volume quota desynchronises actual free space from quota-restricted space and drives endless tiering. Policy compliance is evaluated every 60 minutes, so tiering lags a burst of writes by up to an hour plus processing.

**[Azure File Sync Scale Targets](https://learn.microsoft.com/en-us/azure/storage/file-sync/file-sync-scale-targets)**

- *limits and quotas, Microsoft Learn (Azure Storage documentation).* The authoritative scalability and performance targets table for Azure File Sync, marking each limit as hard (enforced) or soft (Microsoft-tested boundary), plus the published sync-session throughput figures for change enumeration, upload, namespace download, and full download.
- **Why it matters here:** These numbers set the organization's topology cardinality and are the only defensible basis for forecasting the initial sync window and the steady-state object budget across its caching servers - a forecast the customer will hold the consultant to.
- **Take away:** Hard limits to design against: 1 cloud endpoint per sync group, 100 server endpoints per sync group, 30 server endpoints per server, 200 sync groups and 100 registered servers and 100 private endpoints per Storage Sync Service, 100 Storage Sync Services per subscription, and a 64 KiB maximum security descriptor per object (a real constraint on deeply ACL'd organization shares). Soft boundaries: 100 million objects per sync group, 5 million objects in any single non-recursive directory, and 100 GiB per file. For scheduling, use the published rates directly: initial cloud change enumeration runs at 150 objects/sec per sync group and upload at 200 objects/sec per sync group, so splitting data across multiple sync groups is the supported lever to shorten the initial sync - and a change made directly in the Azure file share is not discovered until the cloud change detection job runs, which starts only once every 24 hours.

**[Troubleshoot Azure File Sync cloud tiering](https://learn.microsoft.com/en-us/troubleshoot/azure/azure-storage/files/file-sync/file-sync-troubleshoot-cloud-tiering)**

- *troubleshooting, Microsoft Learn (Azure support documentation).* The official support article for cloud tiering failures, covering why files fail to tier or recall, the Telemetry and RecallResults event logs and their event IDs, the server-local PowerShell cmdlets for per-file tiering and recall results, and a full error-code-to-remediation table for both tiering and recall.
- **Why it matters here:** It is the operational runbook the organization's storage team will need on day one of production, and it names the single diagnostic that identifies a recall storm by culprit application - indispensable when an antivirus, backup, indexer, or classification agent starts pulling the tiered namespace back over the ExpressRoute circuit.
- **Take away:** Telemetry Event ID 9059 (Applications and Services\Microsoft\FileSync\Agent) gives the application recall distribution per server endpoint - ShareId, Application Name, and TotalEgressNetworkBytes - which is the one artifact that names which agent is causing recall egress; pair it with 9005/9006/9009 for recall reliability, error distribution, and session detail, and 9003/9016/9029 for tiering. Use Get-StorageSyncFileRecallResult and Get-StorageSyncFileTieringResult (import StorageSync.Management.ServerCmdlets.dll) for per-file results, and increase the RecallResults log size before go-live or high recall volume will wrap the evidence away. Two errors to pre-empt in a locked-down organization deployment: recall failing with 0x80070005 ERROR_ACCESS_DENIED means the storage account firewall/virtual network rules do not admit the caching server, and 0x80090352 SEC_E_ISSUING_CA_UNTRUSTED means a TLS-terminating proxy is intercepting File Sync traffic. GhostingExclusionList under HKLM\SOFTWARE\Microsoft\Azure\StorageSync controls file types excluded from tiering.

## Data protection and recovery

**[Design a Ransomware-Resilient Backup Architecture by Using Azure Backup](https://learn.microsoft.com/en-us/azure/architecture/security/ransomware-resilient-backup-architecture/)**

- *reference architecture, Microsoft - Azure Architecture Center.* An Azure Architecture Center architecture that protects business-critical data with two independent, immutable backup copies held in separate subscriptions and regions, fronted by a Resource Guard approval boundary, plus a clean-room recovery data flow and an explicit trade-off table.
- **Why it matters here:** Contoso records are a prime ransomware target and the same small team typically administers both the file storage and the backups, so this is the Microsoft-published pattern for placing the Recovery Services vault outside the blast radius of a compromised storage or file administrator - it is the design authority behind every vault-hardening recommendation the consultant will make.
- **Take away:** Two hard rules to lift verbatim: (1) the Resource Guard must be owned by a different principal than the vault admin - ideally in a separate subscription or a separate Microsoft Entra tenant - because a vault admin who holds permissions on their own Resource Guard defeats MUA entirely; (2) locking immutability is a one-way operation, after which retention can only be extended and never shortened, so validate retention against the records-retention schedule *before* locking. Also lift the recovery rule: for a ransomware event restore into a newly provisioned, network-isolated clean environment and validate before promotion - reserve in-place restore for accidental deletion where the estate is known clean.

**[Architecture Best Practices for Azure Files](https://learn.microsoft.com/en-us/azure/well-architected/service-guides/azure-files)** (also cited above)

- *Well-Architected, Microsoft - Azure Well-Architected Framework.* The Well-Architected Framework service guide for Azure Files and Azure File Sync, mapping design decisions to the five pillars with a Reliability design checklist and a configuration-recommendation table that names soft delete, snapshots, and Azure Backup vaulted backup as the expected data-protection posture.
- **Why it matters here:** This is the pillar-level authority a consultant cites when Contoso asks 'why do we need vaulted backup if we already have snapshots and GRS?' - it states that vaulted backup exists specifically to protect against ransomware and source-data loss caused by a malicious actor or rogue admin, which snapshots and replication cannot do.
- **Take away:** The redundancy decision boundary, which constrains the whole DR design: only standard (HDD) SMB accounts support GRS and GZRS - premium/SSD SMB shares and NFS shares do not, and Azure Files never supports read-access geo-redundancy (an RA-GRS/RA-GZRS account is silently configured and billed as GRS/GZRS). Pair that with the guide's retention statement: vaulted backup creates an offsite copy in the Recovery Services vault retainable for up to 99 years, which is the mechanism that satisfies a statutory records-retention schedule.

**[Business continuity and disaster recovery - Cloud Adoption Framework](https://learn.microsoft.com/en-us/azure/cloud-adoption-framework/ready/landing-zone/design-area/management-business-continuity-disaster-recovery)**

- *Cloud Adoption Framework, Microsoft - Cloud Adoption Framework.* The Azure landing zone Management design area for BCDR, listing the platform-level design considerations (RTO/RPO capture, vault limits, ExpressRoute failover bandwidth, data residency) and the design recommendations that govern how backup is provided as a platform capability.
- **Why it matters here:** For a organization, backup has to be a governed platform service with auditable enforcement rather than a per-share afterthought, and this design area is where the ExpressRoute-only connectivity decision and the backup decision meet - it explicitly calls out ExpressRoute peering redundancy and bandwidth capacity planning for failover.
- **Take away:** Two governance rules: 'Use Azure-native backup capabilities... you can set, audit, and enforce backup configurations with Azure Policy to ensure compliance with organization requirements' - so backup posture is a Policy assignment on the landing zone, not a checklist; and treat vault topology as a landing-zone decision, because the design considerations name 'subscription limits restricting the number of Recovery Services vaults and the size of each vault' as a constraint you must design around up front. Also: 'Use multiple regions and peering locations for ExpressRoute connectivity' so a peering-provider outage does not sever cross-premises access.

**[Azure Backup Security Best Practices for Data Protection](https://learn.microsoft.com/en-us/azure/backup/azure-backup-data-protection-best-practices)**

- *security baseline, Microsoft - Azure Backup.* The Microsoft cloud security benchmark (MCSB)-aligned security best-practice article for Azure Backup, organised into four pillars - access control, secure backup storage, data recoverability, and backup governance - and including the BCDR security posture rating model and the built-in Azure Policy definitions.
- **Why it matters here:** It converts 'harden the vault' into a measurable, auditable target Contoso's security office can sign off on and that an auditor can test, which matters when a public-sector customer must evidence its ransomware controls.
- **Take away:** Design to the named **'Excellent' BCDR security level**, whose stated requirements are: either immutability or the soft-delete vault setting must be enabled *and irreversible* (locked / always-on), **and** multi-user authorization must be enabled on the vault. Two supporting numbers: soft delete is configurable up to 180 days with a 14-day default, and the guidance is to set it above 35 days or align it to policy retention. Enforce it with the listed audit policies ('Immutability must be enabled for Recovery Services vaults', 'Multiuser authorization (MUA) must be enabled for Recovery Services vaults', 'Soft delete must be enabled for Recovery Services vaults').

**[About Azure Files backup](https://learn.microsoft.com/en-us/azure/backup/azure-file-share-backup-overview)**

- *product documentation, Microsoft - Azure Backup.* The defining product document for Azure Files backup: it specifies the snapshot tier and vault-standard tier, the step-by-step backup and restore data flow for each, the snapshot lease mechanism, and how restores interact with Azure File Sync.
- **Why it matters here:** This is the document that substantiates the claim that no backup data traverses Contoso network - and it is also the only place that explains the File Sync restore hand-off, which is exactly how a restored file gets back down to a branch office's cached server.
- **Take away:** The data-path facts to put in the design: in the **snapshot tier** the share snapshot is created through the Files API and only the snapshot URL is stored in the metadata store - the data never leaves the storage account; in the **vault-standard tier** Azure Backup identifies changed files and blocks and transfers them to the vault service-to-service, and **only the last snapshot of the day is transferred to the vault** regardless of how many backups you schedule. Two protection mechanics worth quoting: Azure Backup takes a lease of **infinite duration** on every snapshot it creates, so snapshot deletion (and therefore one-click deletion of the backed-up share) is blocked; and configuring backup enables **share soft delete at the storage-account level with a 14-day retention**. Finally, on restore Azure Backup tells the Azure File Sync service the paths being restored, triggering background change detection so changed files sync down to server endpoints *in parallel* with the restore to the share.

**[Support Matrix for Azure Files backup by using Azure Backup](https://learn.microsoft.com/en-us/azure/backup/azure-file-share-support-matrix)** (also cited above)

- *limits and quotas, Microsoft - Azure Backup.* The authoritative supported-configuration and limits reference for Azure Files backup, split by backup tier: supported regions, storage accounts, protection/backup/restore limits, retention ceilings, supported restore methods, and failover behaviour.
- **Why it matters here:** Every scoping assumption in Contoso's backup design - how many shares per vault, how big a share can get before vault-standard stops covering it, whether the help desk can do item-level restores from the vault copy, and whether cross-region restore exists in the chosen region pair - is decided by this page, and getting it wrong is discovered only after the shares are in production.
- **Take away:** The boundary that most often breaks a design: **vault-standard supports a share of at most 10 TB and 10 million files, caps snapshot retention at 30 days, and does not support file-level recovery - full-share restore only** (to original or alternate location). Item-level restore therefore comes from the snapshot tier, which is itself capped at 200 recovery points per share, 6 scheduled backups per day, and 99 individual files/folders per item-level restore. Two more hard gates: the source storage account must have **'Allow storage account key access' enabled** or backup and restore fail, and **a private endpoint on the vault does not apply to Azure Files backup scenarios** (confirming the transfer is service-to-service, not through the customer VNet). Per-vault ceilings are 2,000 protected shares and 200 registered storage accounts. After a customer-managed *unplanned* failover, backups stop and **only cross-region restore from the vault is supported** - and Cross Region Restore is available in all vault-standard regions except Italy North.

**[Data Protection Overview for Azure Files](https://learn.microsoft.com/en-us/azure/storage/files/files-data-protection-overview)**

- *design guide, Microsoft - Azure Files.* The Azure Files data-protection design overview covering the full defence stack for the share and the account: resource locks, storage-account recovery, share soft delete and undelete, share snapshots, redundancy, customer-managed failover, and the Azure File Sync hybrid backup pattern.
- **Why it matters here:** It defines the layer *beneath* Azure Backup - the accidental-deletion and human-error controls on the share and storage account - which is where the majority of a organization's real restore requests actually land, and it is the canonical citation for share soft delete and undelete.
- **Take away:** Build the accidental-deletion stack in this order and state its limits: an ARM **CannotDelete** lock on the storage account (a **ReadOnly** lock also blocks configuration changes), share soft delete for undelete of a deleted share (soft-deleted shares are still billed on used capacity), and **up to 200 snapshots per file share**, billed differentially so multiple recovery points are cheap. The catch worth flagging to the customer: a deleted **storage account** is recoverable only if it was deleted within the past 14 days **and no new account with the same name has been created since** - which is why the lock, not the recovery capability, is the actual control. Also note the redundancy constraint restated here: geo-redundancy (GRS/GZRS) is supported only for HDD file shares; SSD shares must use LRS or ZRS.

**[Best Practices for Disaster Recovery with Azure File Sync](https://learn.microsoft.com/en-us/azure/storage/file-sync/file-sync-disaster-recovery-best-practices)**

- *design guide, Microsoft - Azure File Sync.* The Azure File Sync disaster-recovery design guide, covering server high availability, where backup must be taken in a hybrid deployment, the explicitly unsupported recovery actions, VSS/Previous Versions self-service restore on tiered volumes, and redundancy/failover behaviour of the Storage Sync Service.
- **Why it matters here:** This is the single most consequential document for Contoso's specific topology - on-premises Windows servers caching Azure file shares - because it invalidates the traditional 'the branch file server is backed up by our on-prem backup agent' assumption that Contoso almost certainly still holds.
- **Take away:** The decision rule: **if cloud tiering is enabled, do not run an on-premises backup solution against the server endpoint.** Tiered files will either be skipped (their `FILE_ATTRIBUTE_RECALL_ONDATA_ACCESS` attribute), be backed up as tiered stubs that are unusable on restore, or be recalled to disk at high egress cost - back up the cloud endpoint with Azure Backup instead, because the cloud endpoint always holds a full copy while a server endpoint holds only a subset. Equally important is the explicit unsupported list for any registered server: **restoring tiered files from third-party on-premises backup to a server endpoint, restoring from an OS backup, cloning the server OS or its volumes, and reverting to a VM checkpoint are all unsupported and can cause data loss.** For self-service restore, VSS/Previous Versions *is* supported on cloud-tiering-enabled volumes but must be enabled through PowerShell (increasing snapshot storage cost) and only supplements cloud-side backup - it does not protect against loss of the server itself. Note also that a customer-initiated storage account failover requires a **support ticket to fail over the Storage Sync Service** as a separate step.

**[Azure Verified Module - Recovery Services Vault (avm/res/recovery-services/vault)](https://github.com/Azure/bicep-registry-modules/tree/main/avm/res/recovery-services/vault)**

- *module registry, Microsoft - Azure Verified Modules (Azure/bicep-registry-modules).* The official Azure Verified Module that deploys a Recovery Services vault, published to the public Bicep registry as `br/public:avm/res/recovery-services/vault:<version>` with the vault's full data-protection surface exposed as typed parameters.
- **Why it matters here:** It lets Contoso's vault posture be delivered as reviewable, redeployable infrastructure-as-code rather than a portal walkthrough - which is what makes the hardened configuration auditable, reproducible in a second region for the cross-region copy, and defensible to an auditor asking how the control was applied.
- **Take away:** The module already exposes every control this principle requires, so no bespoke ARM/Bicep is needed: `immutabilitySettingState` (allowed values `'Disabled' | 'Locked' | 'Unlocked'`), `softDeleteSettings`, `backupConfig`, `backupPolicies`, `protectedItems`, `redundancySettings` (`'GeoRedundant' | 'LocallyRedundant' | 'ZoneRedundant'`), `restoreSettings` (cross-region restore), **`resourceGuardOperationRequests`** for multi-user authorization, plus `privateEndpoints`, `publicNetworkAccess`, `customerManagedKey`, `roleAssignments`, `lock`, `monitoringSettings` and `diagnosticSettings`. Ship the vault as a pinned-version module invocation with `immutabilitySettingState` and the Resource Guard operation list set in code, so the 'Excellent' posture is enforced at deploy time and drift is visible in the pipeline.

**[Migration Overview for SMB Azure File Shares](https://learn.microsoft.com/en-us/azure/storage/files/storage-files-migration-overview)**

- *design guide, Microsoft - Azure Files documentation.* The decision guide for SMB file-share migrations: what file fidelity means and which metadata Azure Files can store, how to use Azure Migrate for file-share discovery and assessment, how to size storage accounts and shares, and a source-versus-target matrix plus a tool-fidelity table that ranks every Microsoft copy tool.
- **Why it matters here:** This is the page that turns 'which tool do we use for this share' into a defensible written decision for each wave - and it also documents that the Azure Migrate appliance the organization is already deploying for servers will discover and assess SMB/NFS shares with no extra setup, which folds the file estate into the same discovery exercise.
- **Take away:** Two hard rules. First: set the ACLs on the root directory of the target share *before* copying a large number of files - root ACL changes propagate very slowly after a bulk copy. Second, the fidelity ranking that decides tool choice: Azure Storage Mover, Azure Data Box and Data Box Heavy, RoboCopy and Azure File Sync are full fidelity; **Data Box Disks does not preserve file metadata**; AzCopy (capped around 10 million files per job) and Storage Explorer lose fidelity; Azure Data Factory copies no metadata at all. Also plan around LastAccessTime, which is not supported on the target and always returns CreationTime, and the 250 storage accounts per subscription per region limit (500 with a quota increase).

**[On-premises NAS migration to Azure File Sync](https://learn.microsoft.com/en-us/azure/storage/files/storage-files-migration-nas-hybrid)**

- *design guide, Microsoft - Azure Files documentation.* The eight-phase runbook for moving SMB shares from a NAS appliance onto a Windows Server and into Azure file shares with Azure File Sync, including share-to-file-share mapping, cloud tiering during seeding, the exact RoboCopy command, and the user cut-over phase.
- **Why it matters here:** This is the closest published match to the organization's actual mechanics - Azure File Sync as the seeding path with on-premises caching servers, RoboCopy preserving NTFS ACLs and timestamps, and DFS-N as the cutover and rollback lever - and it explains why Azure File Sync cannot sync a NAS location directly, which is the reason a Windows Server has to sit in the path at all.
- **Take away:** The seeding command, verbatim: `robocopy <Source> <Dest> /MT:20 /R:2 /W:1 /B /MIR /IT /COPY:DATSO /DCOPY:DAT /NP /NFL /NDL /XD "System Volume Information" /UNILOG:<file>` - `/COPY:DATSO` deliberately omits `U` because auditing/SACL data cannot be stored in an Azure file share, and `/IT` is what catches an ACL change plus attribute update between passes. Wave sequence: run it repeatedly until one pass fits the maintenance window, then remove user write access (point DFS-N at a non-existent target or change the root share ACLs), run one final pass, create the share on the Windows Server and repoint DFS-N. Two traps: set cloud tiering to 99% volume free space for the migration and reset it (e.g. 20%) on **every** server endpoint on that volume afterwards - sync applies the most restrictive policy per volume, so one endpoint left at 99% keeps the whole cache empty; and `/LFSM` is only valid when the destination is local storage, never a remote SMB share, and is incompatible with `/MT`. Scale limits for wave sizing: 30 Azure file shares per server, 100 million items per share tested but stay under 20-30 million.

**[Introduction to Azure Storage Mover](https://learn.microsoft.com/en-us/azure/storage-mover/service-overview)**

- *product documentation, Microsoft - Azure Storage Mover documentation.* The service overview for Azure Storage Mover, defining the managed migration service, its agent-based and agentless models, the migration project / endpoint / job-definition resource model, the supported source-to-target matrix, and the documented pattern for combining it with Azure Data Box.
- **Why it matters here:** Storage Mover is the alternative to RoboCopy for the seeding pass and is the tool that makes an Azure Data Box bulk seed viable for the organization's larger shares - it closes the delta accumulated while the Data Box is in transit, which is the part of a Data Box plan customers most often fail to design.
- **Take away:** The named pattern: Data Box for the bulk seed, Storage Mover for the 'online catch-up' delta before cutover - and when only a file's metadata changed (permissions, for example), Storage Mover uploads just the new metadata rather than recopying the file, which is what keeps the catch-up window short. Supported-configuration boundaries to check before committing: SMB 2.x/3.x sources to SMB Azure file shares are full fidelity (folder structure, timestamps, ACLs, attributes preserved), **SMB 1.x sources are not supported**, NFS Azure file shares are not a supported SMB target, and the agentless SMB path requires private network connectivity to the source share plus SMB credentials stored in Azure Key Vault. One Storage Mover resource covers all shares; you deploy an agent near each source.

## Operations and governance

**[Monitor Azure File Sync](https://learn.microsoft.com/en-us/azure/storage/file-sync/file-sync-monitoring)**

- *product documentation, Microsoft Learn (Azure Storage documentation).* The canonical guide to monitoring an Azure File Sync deployment: the Storage Sync Service metric set, the pre-configured 'recommended alerts' with their default thresholds and evaluation periods, the portal health surfaces, and the Windows Server Telemetry event IDs and performance counters that back them.
- **Why it matters here:** This is the source for Contoso's day-one alert set on the Storage Sync Service and for the server-side event IDs the organization's own server team will look at when sync stalls on a caching server, since the caching servers remain on-premises under organization operations while the service metrics live in Azure.
- **Take away:** Lift the recommended alert rules verbatim with their documented defaults rather than inventing thresholds: ServerSyncSessionResult < 1 over a 24 h lookback (sync session failed); StorageSyncServerHeartbeat < 1 over 6 h (server lost contact); StorageSyncLowDiskModeCount >= 1 over 12 h (endpoint in low-disk mode); StorageSyncRecallTotalSizeBytes > 536,870,912,000 (500 GiB) total over 24 h (runaway recall, typically AV/backup/indexer); StorageSyncAgentVersionExpirationDays > 0 over 12 h (agent expiring, ~90-day warning); and Files not syncing > 100. Critically, never set frequency of evaluation below 30 minutes - metrics arrive only every 15-20 minutes and tighter evaluation generates false alerts. Server-side, map health to event IDs 9102 (session complete + HResult + PerItemErrorCount), 9302 (progress every 5-10 min), 9121 (per-item errors), 9301 (server-to-service heartbeat every 30 s), 9003/9016/9029 (tiering) and 9005/9006/9009/9059/9071 (recall).

**[Azure security baseline for Azure File Sync](https://learn.microsoft.com/en-us/security/benchmark/azure/baselines/azure-file-sync-security-baseline)** (also cited above)

- *security baseline, Microsoft Learn (Microsoft cloud security benchmark).* The Microsoft cloud security benchmark mapped control-by-control onto Azure File Sync, stating for each capability whether the service supports it, whether it is on by default, and whether Microsoft or the customer owns the configuration.
- **Why it matters here:** It settles in writing what Contoso can and cannot instrument or protect on the Storage Sync Service itself - the decisive answer when a organization auditor asks why sync-service logs are absent from the SIEM, or why the Recovery Services vault protects the file shares but not the sync service.
- **Take away:** Three hard boundaries to state in the design: (1) LT-4 Azure Resource Logs is **not supported** for Azure File Sync - there are no diagnostic-setting log categories to route to Log Analytics, so sync monitoring is platform metrics plus the server Telemetry event log, full stop; (2) there is no Defender plan for File Sync - apply Microsoft Defender for Storage to the backing storage account instead; (3) BR-1 Azure Backup is **not supported** for the sync service - Azure Backup protects the Azure file shares, and Storage Sync Service configuration must be recovered from IaC. It also confirms Private Link and 'disable public network access' are supported but off by default, i.e. explicit customer actions for an ExpressRoute-only posture.

**[Architecture Best Practices for Azure Files](https://learn.microsoft.com/en-us/azure/well-architected/service-guides/azure-files)** (also cited above)

- *Well-Architected, Microsoft Learn (Azure Well-Architected Framework).* The Well-Architected Framework service guide for Azure Files and Azure File Sync, with per-pillar design-review checklists and configuration recommendation tables, plus explicit Azure Policy and Azure Advisor sections.
- **Why it matters here:** It is the review lens for Contoso's operational and cost decisions - access tier, reservations, snapshot and soft-delete cost behaviour, IaC plus Policy enforcement, Storage insights dashboards - and it is the only Microsoft document that treats File Sync as part of the Azure Files operating model rather than as a separate product.
- **Take away:** The cost decision rule: migrate in on the *transaction optimized* tier (migration is an atypically transaction-heavy workload), then after a few weeks of steady state feed real transaction counts into the pricing calculator - 'most customers should choose cool even if they actively use the share' - and move tiers only when justified, because each move incurs transactions. Deploy one file share per storage account, since standard shares report transaction data only at account level and mixed shares destroy billing attribution. Explicitly budget for the fact that Azure File Sync takes share- and file-level snapshots as part of normal operation, which adds to the Azure Files bill. Operationally: Storage insights for the health dashboard, IaC (ARM/Bicep/Terraform) for the storage accounts, and Azure Policy to enforce their configuration.

**[Monitoring and reporting solutions for Azure Backup](https://learn.microsoft.com/en-us/azure/backup/monitoring-and-alerts-overview)**

- *product documentation, Microsoft Learn (Azure Backup documentation).* The overview of every Azure Backup monitoring and reporting surface - built-in Azure Monitor security and job-failure alerts, metric alerts, Log Analytics and Resource Graph custom alerts, Backup Reports workbooks - including the matrix of which built-in alert fires for which workload type.
- **Why it matters here:** Azure Files shares are an explicitly supported workload in that matrix, so this page defines precisely which backup failures Contoso gets alerted on for free and which need a custom rule - the difference between an alert design that catches a failed organization share backup and one that silently misses it.
- **Take away:** For **Azure Files** the built-in Azure Monitor alerts are only: Backup Failure, Restore Failure, Modify Policy with Shorter Retention, and Modify Protection with Shorter Retention. The security alerts Contoso will most want - Delete Backup Data, Upcoming Purge, Purge Complete - do **not** list Azure Files as a supported workload, so deletion/purge detection for file-share backups must be built as a Log Analytics or Azure Resource Graph alert against vault diagnostic data. Route the four supported alerts to organization recipients using Azure Monitor alert processing (action) rules plus action groups, use Backup Reports (Azure Monitor Logs + workbooks, with scheduled email) for the periodic reassessment evidence pack, and note that classic Backup alerts are deprecated as of 31 March 2026 - do not design onto them.

**[Plan an Azure File Sync deployment](https://learn.microsoft.com/en-us/azure/storage/file-sync/file-sync-planning)** (also cited above)

- *product documentation, Microsoft Learn (Azure Storage documentation).* The deployment planning guide for Azure File Sync, covering supported Windows Server versions, sync topology and share-mapping limits, cloud tiering, networking, antivirus and dedup interaction, and - most importantly here - the agent lifecycle guarantees and automatic-update model.
- **Why it matters here:** It supplies the agent lifecycle and update policy Contoso must write into its operational handover document, and the antivirus rule that is the single largest avoidable egress cost driver on a File Sync estate with cloud tiering enabled.
- **Take away:** The agent lifecycle guarantees are contractual and should be quoted into the handover: major agent versions are supported at least 12 months from release, with at least 3 months of overlap between majors, and registered servers are warned at least 3 months before expiry; minor versions expire with their major (18.*.*.* all expire together); installing an expired agent warns but succeeds, while connecting with one is blocked. Set the policy explicitly with `Set-StorageSyncAgentAutoUpdatePolicy` - `UpdateBeforeExpiration` (default: self-update attempted weekly inside the maintenance window during the last 21 days) as the guardrail, or `InstallLatest` for stay-current, noting InstallLatest is not applicable to clustered servers. Separately: tiered files carry `FILE_ATTRIBUTE_RECALL_ON_DATA_ACCESS` - instruct the organization's AV vendor to skip them or every scan becomes recall egress; Microsoft Defender/SCEP already skip them on on-demand scans.

**[Azure File Sync Scale Targets](https://learn.microsoft.com/en-us/azure/storage/file-sync/file-sync-scale-targets)** (also cited above)

- *limits and quotas, Microsoft Learn (Azure Storage documentation).* The authoritative table of Azure File Sync scalability limits - marked hard (enforced maximum) or soft (Microsoft-tested boundary) - together with measured object-throughput performance targets.
- **Why it matters here:** Capacity and quota management for Contoso's server endpoints depends entirely on these numbers, and the hard/soft distinction tells the consultant which limits are an immovable design ceiling and which are simply the right place to set a monitoring threshold.
- **Take away:** Hard limits to design against: 100 Storage Sync Services per subscription; 200 sync groups, 100 registered servers and 100 private endpoints per Storage Sync Service; exactly 1 cloud endpoint and up to 100 server endpoints per sync group; 30 server endpoints per server; 64 KiB maximum security-descriptor size (a real risk on deeply ACL'd organization shares). Soft (tested) boundaries to alert on rather than assume: 100 million objects per sync group, 5 million objects in a single non-recursive directory, 100 GiB file size, and minimum tierable file size = 2x the filesystem cluster size. Size the migration and the reassessment cadence from the performance targets: 150 objects/sec initial cloud change enumeration and 200 objects/sec upload per sync group, 400 objects/sec namespace download and 60 objects/sec full download per server endpoint - and note that if the Azure file share size limit is reached, sync stops entirely.

**[Operational compliance considerations](https://learn.microsoft.com/en-us/azure/cloud-adoption-framework/ready/landing-zone/design-area/management-operational-compliance)**

- *Cloud Adoption Framework, Microsoft Learn (Cloud Adoption Framework for Azure).* The Cloud Adoption Framework landing-zone design area covering operational compliance - monitoring for configuration drift, in-guest configuration validation, and update management, with named recommendations and the questions to ask the customer.
- **Why it matters here:** This engagement creates two distinct drift surfaces - the Azure resource configuration (storage accounts, Storage Sync Service, vault, private endpoints, Policy assignments) and the on-premises Windows caching servers whose agent and OS patch state must stay current - and CAF is the governance frame that says both belong in one operations baseline Contoso signs up to at handover.
- **Take away:** Split drift control across the two planes and automate both: Azure Policy audit + remediation for Azure resource drift, and Azure Automanage Machine Configuration (the guest-configuration extension) enabled *through policy* for in-server OS/application/environment settings on the caching servers; then use Azure Update Manager as the long-term Windows patching mechanism with its configuration enforced by Azure Policy so no organization server can quietly drop out of the patch regimen. The page also names infrastructure as code as a first-class drift control and points to 'Use infrastructure as code to update Azure landing zones' - which is the hook that makes the AVM-based redeploy part of governance, not just deployment convenience.

**[Remediate non-compliant resources with Azure Policy](https://learn.microsoft.com/en-us/azure/governance/policy/how-to/remediate-resources)**

- *product documentation, Microsoft Learn (Azure Governance documentation).* The how-to for bringing already-existing non-compliant resources into a compliant state via remediation tasks for deployIfNotExists and modify policies, covering the managed identity model, role requirements, and remediation task scale settings.
- **Why it matters here:** Contoso's file estate exists long before the policy set does, so every governance control the assessment recommends - diagnostic settings, private endpoints, secure transfer required, private DNS zone linkage for File Sync - lands on the existing brownfield resources only through a correctly permissioned remediation task, not through the assignment alone.
- **Take away:** The failure mode to design out: role assignments for the policy assignment's managed identity are granted **automatically only in the Azure portal** - assignments created via SDK, CLI, PowerShell or a pipeline must have the definition's `roleDefinitionIds` granted manually, or remediation deployments fail; likewise, editing `roleDefinitionIds` later never re-grants permissions, even in the portal. Remediation is also bounded and must be sized: `ResourceCount` defaults to 500 with a maximum of 50,000 resources per task, `ParallelDeploymentCount` is 1-30 (default 10), and `FailureThreshold` defaults to 100%. Use a user-assigned managed identity so the identity survives assignment churn, and scope `roleDefinitionIds` to the minimum role.

**[Azure Verified Modules - Bicep Resource Modules index](https://azure.github.io/Azure-Verified-Modules/indexes/bicep/bicep-resource-modules/)**

- *module registry, Microsoft (Azure Verified Modules, github.com/Azure).* The published index of every Azure Verified Modules Bicep resource module with its `br/public:avm/res/...` reference and lifecycle status - the single list of what Microsoft maintains as a verified module today.
- **Why it matters here:** The IaC recommendation for Contoso should be AVM-first so it inherits Microsoft-maintained defaults for diagnostic settings, RBAC, locks and private endpoints instead of hand-rolled templates - but the index is equally valuable for showing exactly where AVM stops for this particular workload, which is a scoping fact the consultant should surface before the customer budgets the IaC work.
- **Take away:** There is **no AVM module for Microsoft.StorageSync** - the Storage Sync Service, sync groups, registered servers and server endpoints must be authored as native Bicep resources (and their private endpoints and private DNS zone groups wired manually) inside an otherwise AVM-based deployment. Everything surrounding them is covered and should be reused rather than rewritten: `avm/res/storage/storage-account` (verified separately in the registry, with file services, diagnostic settings and private endpoints), `avm/res/recovery-services/vault` (vault plus backup policies, protection containers, private endpoints, diagnostic settings, locks and CMK), and the Azure Monitor layer - `avm/res/insights/metric-alert`, `avm/res/insights/action-group`, `avm/res/insights/diagnostic-setting`, `avm/res/insights/activity-log-alert`, `avm/res/insights/scheduled-query-rule` and `avm/res/insights/data-collection-rule` - which is precisely how the recommended File Sync alert set and its action groups should be codified and redeployed.

**[Azure file shares in a hybrid environment](https://learn.microsoft.com/en-us/azure/architecture/hybrid/azure-file-share)**

- *reference architecture, Microsoft Learn (Azure Architecture Center).* The Azure Architecture Center reference architecture for hybrid Azure file shares - AD DS identity-based SMB authentication, ExpressRoute/VPN access paths where TCP 445 is blocked, an optional Recovery Services vault, and Azure File Sync caching - with Well-Architected considerations for manageability, availability and cost.
- **Why it matters here:** It is the Microsoft-published shape Contoso's design should be recognisably an instance of (it explicitly names ExpressRoute as the access path when port 445 is unavailable, matching the ExpressRoute-only requirement), and its manageability section carries two operating constraints that change how backup and capacity are governed at handover.
- **Take away:** Two governance side effects to document explicitly in the runbook: (1) configuring Azure Backup for the *first* Azure file share in a storage account enables soft delete for **all** file shares in that account - an account-wide change Contoso did not explicitly request, which also alters billing because soft-deleted shares bill on used capacity; and (2) a share supports at most **200 snapshots**, and deleting the share deletes its snapshots - that ceiling, not the policy UI, is the real limit on backup frequency x retention, since Azure Backup for Azure Files is snapshot-based. It also restates the capacity rule that IOPS and throughput limits are per storage account and shared across all shares in it, so each organization share belongs in its own storage account.
